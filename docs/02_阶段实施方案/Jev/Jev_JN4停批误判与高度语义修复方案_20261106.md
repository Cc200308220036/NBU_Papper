## 1. 问题与定位

### A：批次范围判断误报——已确认的代码缺陷

证据为`semantic_pallet_planner/outputs/JEV_JN4_SYNTH_EXEC_20261105_01/run/jobs/J0006/`。第二单几何方法在14次STABLE后出现1次UNASSESSABLE，终止原因为已登记的`POSE_HEIGHT_MISMATCH`。

`packaging_evaluation_orders.py:254—257`从`metrics.json`取整个`monitor_reasons`字典，将其全部键与`allowed_range_reasons`比较。该字典同时包含成功原因`CONTACT_NETWORK_BALANCED:14`和不可评价原因`POSE_HEIGHT_MISMATCH:1`。成功原因不属于不可评价白名单，故误报`UNREGISTERED_MONITOR_SCOPE`并停止整批。

`packaging_metrics.py:job_metrics`汇总所有监测原因用于统计，这个统计本身没有错；错误在调用方把它当作不可评价原因集合。`packaging_memory_pilot.py:292`附近存在相同使用方式，需要纳入同源问题审查，不能据此改写旧运行。

现有`test_packaging_evaluation_v10_stops.py`在第一个动作就注入不可评价，未覆盖“先多次成功，再发生不可评价”的混合原因情况，因此没有触发本缺陷。

### B：高度不一致——已确认是几何语义边界，不是数值误差

失败决策`J0006_D0014`，箱体`SYN_COMBO_02_I0017`，候选`E2_2bff7b1c942b3487`：

| 对象 | x区间mm | y区间mm | z区间mm |
|---|---|---|---|
| 待放箱 | [-590,-210] | [205,405] | [0,140] |
| 已放I0012 | [-350,200] | [125,405] | [180,290] |
| 已放I0010 | [-370,200] | [255,405] | [290,490] |

三个箱体在水平投影上有交集，但待放箱与上方两箱在高度方向不相交；待放箱顶面140mm与最近上方箱底180mm之间有40mm间隙。

- `planner/constraints.py:evaluate_pose`检查最终三维位置是否碰撞，并允许地面空隙位置，不检查从上方进入该位置的运动路径。
- `stability/balance_adapter.py:134—141`调用`Space.interSect2D`计算下落高度，并与候选精确底面高度比较。
- `stability/vendor/pct/space.py:306—316`取水平投影重叠箱体的最高顶面，所以计算为490mm；候选底面为0mm，差值490mm，按现有合同返回UNASSESSABLE。

这说明候选器的最终位置语义与PCT下落几何不完全一致。现有主任务没有授权新增机器人路径可达性限制；也不能从最终位置无碰撞推断实际机械臂可进入。该动作不是预测静态失稳，未提交，STOP前后状态相同。

## 2. 推荐的最小修复：先修A，B保持范围停单

### 修改位置与拟议接口

在公共运行层新增一个小型只读辅助函数，拟议签名为：

```python
unassessable_reasons_from_checkpoint(checkpoint) -> set[str]
```

它只读取已保存事件及适用的pending_event，从`monitor.status == "UNASSESSABLE"`的结果提取`reason_code`。校验终止事件确实为不可评价、结果/原因非空；缺失或记录矛盾仍按技术失败停止，不猜测原因或给默认通过。

`packaging_evaluation_orders._run_plan`及同源的`packaging_memory_pilot`范围检查复用该函数，以提取出的不可评价原因集合检查冻结白名单。`STABLE`原因不参与；`ERROR`、UNKNOWN_SEND、watchdog及未登记不可评价原因仍按原规则停批。

不修改`monitor_reasons`统计含义，不把`CONTACT_NETWORK_BALANCED`加入不可评价白名单，不扩展旧封闭Schema。本修复属于运行编排源码变更，仍会改变源码身份，但不需要改变PCT算法版本。

### 修复后的预期行为

以本次状态为例：第二单几何方法仍停在14/20箱，记`UNASSESSABLE/POSE_HEIGHT_MISMATCH`；失败动作不提交、不移出缓冲、不改选。由于原因已登记，批次可以按冻结顺序执行第二单的下一个方法，而非误停整批。修A不会把该订单变成完整完成。

### 必要验证，不调用真实模型

1. 混合原因回归：多次STABLE后接已登记UNASSESSABLE，订单停止，批次正常进入下一job。
2. 未登记原因、缺失原因或损坏监测记录：仍停止整批，后续槽位NOT_RUN。
3. ERROR、UNKNOWN_SEND及技术停止后的再次调用：不派发后续、不重发、不退款。
4. 首批PASS与接续范围：门槛及已有记录不被改写，后续范围不因普通resume扩大。
5. 保存事实恢复：失败动作不提交，已提交动作不重复提交，保存监测不重新计算。

新增重点覆盖混合原因场景，复用现有v10/v11及适用v9测试组织，不跑全量历史测试。可以读取旧J0006记录验证原因提取，但不得重签或重新执行旧job。
