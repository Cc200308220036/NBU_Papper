# Jev JN4 合成订单装入量差异化改造方案

日期：2026-11-07；基线 HEAD 以本文件落盘时实际 `git rev-parse HEAD` 为准。状态：**方案文档，未改码、未生成数据、未调用模型、未消耗任何 API 额度。**

本方案只解决一个经证据定位的问题：**当前合成订单几乎不产生装入量差异，导致 T/E 经验的有效性无法被观测。** 目标是在不破坏既有历史证据、不改物理内核的前提下，构造出"选择真正决定装入量"的订单，并给出"Jev+经验提升装配能力"可被证伪的实验设计。

---

## 1. 问题定位（基于已保存事实，不含推测）

### 1.1 直接现象

`JEV_JN4_SYNTH_RUN_20261106_01` 首任务六方法**全部 COMPLETE 16/16**，固定容器利用率六方法完全相同（0.299965），差异只剩垛高/包络；4 对比较全部落 `COMPACTNESS` 层，`improved` 无法归因于装载能力。其余 20 对 `NOT_RUN`。

### 1.2 根因诊断（逐项有数据支撑）

| 编号 | 根因 | 证据 |
|---|---|---|
| D1 | **体积余量过大** | `SYN_COMBO_01` 需求体积 305,964,000 mm³ / 容器 1,020,000,000 mm³ = **0.300**；粗估容量 48 箱 vs 需求 16 箱（3 倍余量） |
| D2 | **首块恰是最容易的一单** | 六任务体积比 0.300 / 0.519 / 0.528 / 0.681 / 0.855 / 0.735；GATE 固定 `first_task=SYN_COMBO_01`（最易），信息量最低 |
| D3 | **容器载荷从不生效** | 最大总质量 238.8 kg vs `max_payload_kg=1000`；全任务最多只有 `SYN_COMBO_05` 接近体积边界，质量一项始终闲置 |
| D4 | **每箱承载很少生效** | 候选拒绝直方图：`SYN_COMBO_01` 共 15,558 次枚举中 `overload` **0** 次；`SYN_COMBO_01` 的 T/E 两方法分别仅 18 / 12 次；`out_of_bounds`(8,444) 与 `overlap`(5,137) 才是主导 |
| D5 | **可堆叠属性几乎恒真** | 六任务 `stackable` 计数 15/16、17/20、21/24、28/30、33/34、37/40 → 不可堆叠少 1–3 箱，约束几乎不激活 |
| D6 | **业务语义被掏空** | `packaging_synthetic_data.generate()` 固定 `fragile=False`、`product_category='general'`、`rules=[]` → 经验无"可学的语义内容"，只能学到几何常识 |
| D7 | **难度来自落箱模型而非策略** | `SYN_COMBO_02` 几何方法停于 14/20，`monitor_reasons={CONTACT_NETWORK_BALANCED:14, POSE_HEIGHT_MISMATCH:1}` → 属**不可评价范围**，不是方法装不上；该结论在既有报告中已被正确标注 |
| D8 | **经验库与新任务分布不匹配** | 现有 T/E 由装不满、无负载冲突的旧任务分叉材料提炼；在 over-demand 任务上不足以提供可用条件化建议 |

### 1.3 结论

> 当前不是"经验无效"，而是**实验环境没有给经验留下可观测的作用窗口**：装入量主指标在 D1–D5 下饱和，语义内容在 D6 下缺失，部分难度以 D7 形式被吞进 `UNASSESSABLE`。

因此改造方向不是改算法，而是**改数据与约束的活跃度**。

## 2. 改造目标与"可观测性"判据

定义订单 `T` 在方法集合 `M` 上"可观测装入量差异"，当且仅当同时满足：

| 判据 | 定义 | 用途 |
|---|---|---|
| **O1 需求超出可得** | `需求体积 > 本地几何基线实际可达体积` 且 `需求体积 ≤ 1.35 × 容器体积` | 使装入量成为区分指标而非饱和值 |
| **O2 基线下界不塌** | 本地几何基线完成率 ∈ [0.55, 0.90] | 既有提升空间，也不至于全部空池 |
| **O3 约束竞争** | 至少两类硬/软约束在不同方法间产生**不同放弃顺序**（高度 vs 承载 vs 边界） | 产生"选择决定结果"的分歧 |
| **O4 语义非空** | 至少 2 条可确定性判定、且模型可见的软规则在候选中产生真实歧义 | 经验有可学内容 |
| **O5 本地可分化** | **本地两方法（几何 / 固定顺序）即已产生装入量差异** | 零 API 成本预检门槛，见 §6 |

O5 是核心门槛：**若两个本地方法都不分化，说明任务仍无区分度，禁止花 API 额度。**

## 3. 改造方案

改造分三层，**可独立实施、按套餐组合**。所有改动均遵守项目既有纪律：不动物理内核、不动 PCT、不改旧 Schema、不重签历史证据。

### 3.1 A 层：难度与容量（制造 over-demand）

#### A1 ★ 延长任务长度 `n`（首选杠杆，前缀安全）

关键性质（已在代码中核实）：抽样 token 为

```python
token = digest([GENERATION, 20261105, task_id, i])   # 仅依赖 i
item_id = f'{task_id}_I{i:04d}'
```

因此**把 `n` 从 16 延长到 24，前 16 箱的记录完全不变**（同一 token、同一 pool index、同一 item_id）。这意味着可以"在同一前缀上加深需求"，且新增箱体可逐字节核对前缀一致性。

推荐做法：
- 保留 `TASKS` v1 常量不动，新增 `TASKS_BY_GENERATION` 版本化表；
- 新增 `jev_synthetic_combo_generation_v2`（seed 另定），只改任务长度，不改采样规则；
- `n` 的取值由 §4 的**确定性标定流程**给出，不在本文件硬写。

#### A2 ★ 收紧容器载荷（让"重物低放/承载保留"有物理后果）

当前 `max_payload_kg=1000` 完全闲置。改为由订单自身质量决定：

```
max_payload_kg = ceil(0.85 × 订单总质量)
```

例如 16 箱订单总质量 81.82 kg → 载荷上限约 70 kg。此时"先放重箱还是先清空空间"开始影响能否继续放箱。
容器字段是任务自带属性（`packaging_load_task_v1.container` 未锁定具体数值），因此**不改 Schema**。

#### A3 可选：低矮容器分层（制造高度压力）

另设一层 `container.max_height_mm = 600`（长度/宽度不变），迫使方法在"横向铺开"与"向上叠"之间取舍。
**注意**：这会改变容器几何契约的适用性，建议作为**独立分层**报告，不与 A1/A2 主对照混算。

#### A4 可选：承载档位整体下调（让 `overload` 成为高频拒绝）

需要修改包装档位（0/9/27/54 kg 与 0.10/0.25/0.45/0.20 概率）。
**这是本方案中身份影响最大的一项**（见 §5，`CONFIG_SHA256` 硬编码），仅在 A1+A2+B 仍不足以产生 O3 时启用。

### 3.2 B 层：恢复可判定业务语义（给经验可学内容）

现状 `fragile=False`、`product_category='general'`、`rules=[]`，语义层完全空缺。建议新增以下**软规则**（硬约束不变，安全性不降低）：

| 规则 ID | 自然语言（模型可见） | 确定性判定 | 冲突来源 |
|---|---|---|---|
| **R1 重物低放** | "重物应尽量放在较低位置" | `mass_kg ≥ q75(本单质量)` 的箱体满足 `z_base ≤ 0.40 × max_height` | 与"底层承载档位低"冲突 |
| **R2 易碎保护** | "易碎品尽量放上层，且不承担其他箱体" | `fragile=True` 箱体上方支撑计数 = 0，或其上方累计载荷 ≤ 2 kg | 与"底层面积利用率"冲突 |
| **R3 品类集中** | "同类商品尽量集中码放" | 同 `product_category` 箱体质心两两距离 ≤ 0.5 × 容器对角线 | 与"紧凑性几何最优"冲突 |
| **R4 承载保留** | "为后续可能到达的重箱保留承重余量" | 未到货存在 `mass ≥ q75` 时，任一 `capacity ≥ 27 kg` 的顶面占用率 ≤ 70% | 与"尽快填满"冲突 |

实现要点：
- `fragile` / `product_category` 用与 `profile_for` 相同的**哈希分档**机制按 `sku_id` 生成（同 SKU 跨任务一致，可复现）；当前 `runtime_task()` 强制写死 `general`，需**新增视图版本**（见 §5）。
- 规则以**自然语言 + 结构化摘要**进入模型请求，隐藏真值只用于评价（沿用主规范 §4.1 的信息边界）。
- 语义得分进入**并列主指标**，不与装入量加权合成。

> 明确不做：不恢复旧"食品/清洁品相容性""区域约束""AST 生成"路线（主规范已关闭）。

### 3.3 C 层：约束冲突注入（让"选择"真正决定结果）

在 A+B 之上，用**事前登记**的构造规则制造可判定冲突（不改抽样）：

| 冲突 | 构造方式 | 期望观测 |
|---|---|---|
| **C1 高度×承载** | 把本单最重的 2 箱排在最前到货，且其候选仅落在 `low`(9 kg) 档位顶面上 | "低放违反承载" vs "高放违反 R1"二选一 |
| **C2 容量保留** | 前 4 箱为小箱（易填），第 5–8 箱为同底面积大箱 | 是否提前保留连续顶面 |
| **C3 可堆叠稀缺** | 提高 `no_support` 比例（需 A4），迫使"上层只能用少数箱体作基座" | 装箱顺序与基座选择差异 |

C 层必须在**生成前登记**，且不得按任何方法的结果回头调整（否则污染因果）。

### 3.4 D 层：评价口径

| 项 | 现状 | 改造 |
|---|---|---|
| 主指标 | 稳定完整完成 → 装入体积比例 → 件数/质量 Pareto → 紧凑性 | **保留 v2 层级**，但新增 `jev_branch_comparison_rule_v3`：在 over-demand 下把"装入体积比例"提为第一可比层，紧凑性降为末层 |
| 语义指标 | 无 | 新增 `semantic_rule_score`（R1–R4 满足率，分项报告） |
| 诊断 | `EMPTY_POOL` 单一标签 | 拆为 `NO_CANDIDATE` / `HEIGHT_SEMANTIC_UNASSESSABLE` / `MONITOR_UNASSESSABLE` 三类，避免把 D7 类问题算作策略劣势 |

### 3.5 E 层：稳定性与可评价性（不改算法，只改诊断）

- 沿用已修复的批次范围检查（A 部分），不重开 PCT 高度边界（B 部分保留）；
- 在指标中显式记录"终止时的候选拒绝直方图"，使 `EMPTY_POOL` 可归因（边界/重叠/支撑/超载各占多少）；
- **不改** `planner/*`、`evaluation/geometry_oracle.py`、PCT —— 否则 `physical_manifest()` 变化会使全部历史 plan 报 `source_changed`。

## 4. 难度标定流程（确定性，不看模型结果）

**原则：难度只由本地几何基线的完成率决定，任何模型输出不得参与选参。**

```text
步骤1  固定 seed / generation_version / 采样规则，只改任务长度 n
步骤2  对候选 n ∈ {原n, 1.2×n, 1.5×n, 1.8×n} 各生成一版任务
步骤3  用「本地几何基线（local_geometry_test_double）」在 6 个任务上跑，0 次 API
步骤4  计算每任务的：
         - 完成率 = 已提交箱数 / 需求箱数
         - 装入体积比例
         - 终止时候选拒绝直方图
步骤5  选取使「6 任务完成率中位数 ∈ [0.55, 0.90]」的最小 n
        若同一 n 下完成率离散度 > 0.30，则保留多档 n（难度谱）
步骤6  冻结 n 表 → 生成正式数据 → 静态复核 → 提交质检
```

可选补充：用 `local_first_test_double`（固定顺序基线）并行跑一遍，计算

```
Δ_local = 完成率(几何) − 完成率(固定顺序)
```

**Δ_local ≥ 5 个百分点** 才算通过 O5 门槛（本地即分化），否则返回步骤2 调整。

## 5. 对已冻结身份的影响评估

### 5.1 总原则

本项目身份链是：`registration → dataset.data_identity → plan → run`，并叠加 `source_manifest / physical_manifest / config digest / schema 版本 / evaluation rule`。任何改动必须**新增版本并集中路由**，禁止原地修改旧常量或旧 Schema。

### 5.2 逐项影响表

| 改造项 | 必须改动的对象 | 影响的身份 | 旧证据可否重建 | 风险 |
|---|---|---|---|---|
| **A1 延长 n** | `packaging_synthetic_data.TASKS` 需版本化为 `TASKS_BY_GENERATION`；新增 `generation_v2` 常量 | `registration.tasks`、`dataset.data_identity`、plan、run | ✅ 可（旧 generation_version 仍路由 v1） | 🔴 **高**：当前 `generate()` 有 `require(registration['tasks']==TASKS)` 硬校验，原地改常量会导致**旧数据无法重建**，必须做版本路由 |
| **A2 收紧 payload** | `generate()` 支持 container 覆盖（现为深拷贝模板 `NEW_00100027_controlled_heterogeneous.json`） | `dataset`、`plan` | ✅ 可 | 🟡 中：`packaging_load_task_v1.container` 无锁定值，无需改 Schema |
| **A3 低矮容器层** | 同上；新增分层名 | `dataset`、`plan`、分层统计 | ✅ 可 | 🟡 中：需在评价中单列，避免与主对照混算 |
| **A4 承载档位下调** | **必须新增 `configs/packaging_load_v2.json`** + 新 `CONFIG_SHA256` + `packaging_spec(version)` 路由 | `packaging_config_digest`、`packaging_spec()` 的全部调用方、`DATA_JEV_PACKAGING_LOAD_*` | ✅ 可 | 🔴 **高**：`dataset_packaging.CONFIG_SHA256` 是硬编码常量，改文件即触发 `packaging_config_not_frozen` |
| **B 语义规则非空** | `packaging_load_task_v1.schema.json` 有 `rules: {"const": []}`、`regions: {"const": []}` → **必须新增 `packaging_load_task_v2`** | task Schema、runtime、plan、评价 | ✅ 可 | 🔴 **高**：旧 Schema 封闭，塞非空 rules 会直接校验失败 |
| **B fragile/category** | `generate()` 新增哈希分档；`packaging_runtime.runtime_task()` 当前强制 `product_category='general'`、`attributes.cargo_category='general'` → **必须新增 runtime 视图 v12** | `jev_decision_context_v11 → v12`、config、Schema、plan | ✅ 可 | 🟡 中：现视图会静默丢弃语义属性，若只改数据不改视图，模型仍看不到 |
| **C 冲突注入** | `generate()` 新增事前登记的构造步骤 | `dataset`、plan | ✅ 可 | 🟡 中：必须登记在生成前，不能按结果调 |
| **D 评价 v3** | `packaging_reanalysis.RULE` | `plan.evaluation_rule` | ✅ 可 | 🟢 低：新增 rule 常量即可 |
| **D 语义指标** | `packaging_metrics` 新增 `semantic_rule_score` | 指标 Schema、plan | ✅ 可 | 🟢 低 |
| **E 诊断拆分** | `packaging_metrics` / 终止原因枚举 | 指标 Schema | ✅ 可 | 🟢 低 |
| **候选器 / 物理内核 / PCT** | —— | —— | —— | 🔴 **禁止改动**：`physical_manifest()` 含 `planner/generator.py`、`evaluation/geometry_oracle.py` 等，任何改动使全部历史 plan 报 `source_changed`，等价于把所有旧证据作废 |

## 6. 实施顺序与成本

| 阶段 | 内容 | API 成本 | 出口条件 |
|---|---|---:|---|
| P0 | 本地难度标定（§4，含 `n` 扫描与 Δ_local） | **0** | O2 + O5 通过 |
| P1 | A1+A2+B+D 最小套餐实现与构造测试 | 0 | 旧版回归通过、新身份可重建 |
| P2 | 正式数据生成 + 静态复核 + 五类篡改拒绝 | 0 | 数据/计划冻结 |
| P3 | **T/E 重建**（在新分布上重跑 JN2 分叉 → JN3 提炼/审核） | 少量 DeepSeek | 非空且通过审核的卡片 ≥ 6 |
| P4 | 六方法正式运行（含无关 E 消融） | 见 §7 预算 | 完整分母落盘 |
| P5 | 分析交付 | 0 | 预注册判据逐项核对 |

> P3 不可省略：现有 T/E 库由"装不满、无负载冲突"的旧任务提炼，与 over-demand 分布不匹配。**用旧库直接测新分布，等于让经验回答一个它没学过的问题。**

## 7. 实验设计：如何证明"Jev+经验提升装配能力"

### 7.1 方法矩阵（复用现有六方法，不改注册）

```
几何基线 / 固定顺序基线 / Jev无经验 / Jev+T / Jev+E / Jev+无关E
```

无关 E 是必要消融：若 E 的优势被无关 E 复制，说明收益来自**提示长度**而非经验内容。

### 7.2 任务与样本

- 任务：6–8 个 over-demand 合成订单（难度谱覆盖完成率 0.55–0.90）；
- 每任务 × 6 方法 × 2 次重复（模型低温仍非确定，需估计重复方差）；
- 建议 **≥ 72 个远程槽位**；发送上限按任务箱数逐 job 冻结，不使用"未来上限"当预算；
- 训练任务与展示任务**必须分组隔离**（不同 `source_group_id` 与 `order_related_source_groups` 排除），避免经验与测试同源。

### 7.3 主指标与预注册判据

| 层级 | 指标 |
|---|---|
| 主 | 装入体积比例（over-demand 下即为装配能力） |
| 主 | 语义规则得分（R1–R4 分项 + 总分） |
| 次 | 稳定完整完成率、件数/质量装入比例、垛高/包络利用率 |
| 次 | 预测静态失稳停单比例、不可评价原因、技术错误 |
| 成本 | 请求数、token、时延、费用（不可得记 UNKNOWN） |

**预注册"有效提升"判据（三条件同时满足才可声称）：**

1. **方向稳定**：`E vs 无经验` 在 ≥ 2/3 任务上 `improved`（配对评价 v3）；
2. **幅度最小**：中位装入体积比例提升 ≥ 3.0 个百分点，且语义得分提升 ≥ 0.10；
3. **机制排他**：`无关E vs 无经验` 不出现系统性 `improved`（improved 比例 ≤ 1/3）；
4. **不牺牲安全**：硬约束违规、预测失稳停单比例无显著上升。

任一条不满足 → 结论写 `NOT_ESTABLISHED`，并保留全部负例与分母，不得改阈值重跑。

### 7.4 必须同时报告的负向证据

- 全部 `EMPTY_POOL` / `UNASSESSABLE` / `NOT_RUN` 槽位；
- 同状态同候选下的"选了同一动作"比例（暴露 ≠ 使用）；
- T 与 E 的差异（若 E 不胜 T，须明说）；
- token / 时延增量（经验不是免费的）。

## 8. 风险与退路

| 风险 | 表现 | 应对 |
|---|---|---|
| **R1 过度 over-demand** | 所有方法都在很少箱数即 `EMPTY_POOL`，差异退化为噪声 | §4 标定把完成率约束在 [0.55, 0.90]；必要时降低 n |
| **R2 语义规则不可判定** | 规则与几何耦合，评价器无法给稳定得分 | 每条规则必须可写成确定性谓词 + 单元测试反例 |
| **R3 身份链断裂** | 误改 `TASKS` / `packaging_load_v1.json` / 物理内核 → 旧证据不可重建 | §5.2 红项一律"新增版本 + 路由"，禁止原地改 |
| **R4 经验-测试同源** | 训练任务与展示任务共享 `source_group` | 强制 `order_related_source_groups` 排除并在收据中核对 |
| **R5 收益仍不显著** | 三条件不满足 | 按主规范 13.4 退路：论文主线收缩为"候选受限语义决策 + 闭环"，经验作为系统贡献而非收益主张 |
| **R6 工期** | P3 重建 T/E 耗时长 | 可先用"T 案例库"单独验证；E 不通过不影响 T 的结论 |

## 9. 明确不做

- 不改 `planner/generator.py`、`planner/constraints.py`、`evaluation/geometry_oracle.py`、PCT 任何字节；
- 不改 `packaging_load_v1.json`（如需调档位则新增 v2）；
- 不改任何已冻结 Schema，全部新增版本；
- 不恢复旧食品/清洁品、区域、AST 路线；
- 不按模型结果调难度、换 seed、删难单；
- 不把 `EMPTY_POOL` 解释为全局不可装；
- 不把公共硬过滤造成的零违规当作经验收益。

## 11. 一句话总结

> 现在的合成订单"装满得太容易"，所以经验没有可表现的空间。**不改算法，只把需求加长、载荷收紧、语义打开、冲突注入**，并用"本地几何基线完成率"这一**不看模型**的确定性规则来标定难度；所有改动一律新增版本、保留旧身份，再用带无关 E 消融的六方法矩阵验证 `E/T vs 无经验` 是否在装入体积与语义得分上稳定提升。
