# Jev J4 B2真实经验库建设改进方案

编制日期：2026-10-31。状态：**方案已编写，以下新增协议、代码、采集、生成、审核与验收均待实施**。

本方案对应B2-B交付后的五项缺口：合法真实候选、独立来源支持、独立语义审核、真实非空M0、满足条件后的真实合并。它是下一批实施建议，不修改旧冻结结果，不把本批工程完成改写成整个B2研究验收通过，也不替代J4-C收益验证。

## 1. 结论与实施目标

建议按“冻结诊断 → 改进输入与输出合同 → 新增独立训练来源 → 一次性真实提炼 → 独立审核与合并 → 新冻结包及非空M0验证”的顺序推进。

优先解决生成正文混入溯源标识符的问题，同时保留严格引证；随后新增两个独立来源组、每组B1/B2两个训练episode，构成四条新轨迹的小规模试验。跨来源有效父卡出现后，才考虑一次合并与重新审核。只有实际通过支持、审核、冲突和预算门槛的卡才能激活。

**目标是建立可信的非空库准入过程；非空结果不能保证。** 如果新模型输出仍不合法、两个来源不支持同一经验、审核否决或适用条件无法满足，应交付完整失败证据及合法空库，不降低门槛。

本次文档编写不执行新增采集或模型请求，不读取凭证，不代填独立审核结论。后续实施沿用已有授权范围；新增采集及实验范围需在具体执行协议中明确登记，不因文档存在自动生效。

## 4. 工作包一：修复正文与证据组织

### 4.1 当前接口风险

现有`memory_generation.py`的请求同时提供真实episode/decision身份，并要求精确证据链接；生成器容易在`observed_evidence`、`comparison_basis`等自然语言字段复述这些身份。`memory_validation.py`对正文统一检查历史标识符，三条建议因此正确拒绝。

现有`memory_retrieval.card_text()`实际拼接`applicability`、`advice`、`observed_evidence`、`limitations_counterexamples`，所以`observed_evidence`并非仅供本地审计。`comparison_basis`目前不注入，但仍属于正文校验范围。改进不能简单放宽正则，或假设证据段永远不会送入Jev。

### 4.2 拟议合同

以下为待开发版本名，不能当成当前CLI已经支持：

| 层 | 拟议版本/内容 | 规则 |
|---|---|---|
| 训练总结投影 | `training_summary_public_v2` | 保留实际动作、公共状态、资源、反馈、终局和完整覆盖；引入稳定请求内别名及字段语义字典 |
| 生成输出 | `memory_generation_output_v2` | 可注入正文与结构化证据引用分栏，拒绝额外字段与正文身份串 |
| 经验卡 | `jev_memory_card_v3` | 正文、比较依据、观察/假设、证据映射、父卡、审核及版本绑定明确 |
| 提示/渲染/审核 | 分别显式v2 | 三者摘要进入新包身份；实际渲染字段清单单独冻结 |
| 快照与索引 | 按实际结构变更升级 | 即使BM25公式不变，文档正文变更也必须重建索引并冻结新身份 |

卡版本与现有Jev运行协议v3不是同一版本号空间。旧卡/旧包按其原合同加载和渲染，不自动按新规则重解释；遇到不支持的版本明确失败。不得用宽松回退绕过Schema或证据验证。

### 4.3 正文与溯源分离

模型输出分成两部分：

- **可注入正文**：适用条件、观察性建议、概括观察、限制/反例。不得包含episode、source group、decision、原始订单/物品身份或候选编号；保留理解建议必要的公共属性、数值、单位和条件。
- **结构化引证**：引用请求内事实槽位，并标注support/counterexample/unknown；事实槽位由本地确定性代码解析为真实请求、episode、decision、JSON pointer、类型和值。

建议事实槽位形态为`F0001`，事件别名`E0001`，对象别名`O0001`。这些别名仅用于请求内组织和结构化引证，不得写入可注入正文。真正的全局身份与映射保留在本地审计附件，代码不自动改写生成器的自然语言来求通过。

事实表必须包含生成器判断所需的实际数值、单位、上下文和字段语义，不能只给不透明编号。所有被引用事实必须真实出现在对应wire请求内。分别冻结逻辑请求身份、实际messages摘要、wire摘要和覆盖表，避免用“请求包含自身摘要”的循环定义。

### 4.4 跨事件对象与反馈语义

现有导出按每事件的placed/available对象构建B别名，跨事件相同字符串是否指同一对象需要显式验证。新增映射须依据封存事件的真实身份关联，在对象首次公开出现时分配稳定请求内别名；原始身份只保留本地。不得根据尺寸相同推定同一对象，也不得借完整未来序列预分配并泄漏未到达信息。无法确定关联时禁止该跨步资源推论，保留身份未知原因。

建立字段语义字典并逐项对照实际评价器：`instances`、`new_instances`、`coverage.checked`、`coverage.deferred`、业务标签载荷、物理承载限值及终局指标。特别检查“规则已检查”和“规则满足”是否被混淆。字段名或计数存在不证明成功；原建议中的这类表述只列为待审风险，不能在诊断完成前宣称语义错误已证实。

业务标签顶面载荷与物理承载能力分开呈现；重量、坐标、面积及累计载荷统一明确单位。终局结果写成事后观察，不能推导“选择另一动作必定更好”。

### 4.5 提示与校验策略

提示明确每个字段允许什么身份信息；给出纯格式示例，使用占位语义或明确标记的合成fixture，避免把人工优质策略当作真实教师。提示允许返回空建议，不要求正收益，不强迫把规则复述包装成策略。

先固定模型和采样配置，隔离提示/投影/输出合同这一组变化：仍使用官方DeepSeek、`deepseek-flash`，显式关闭thinking，temperature=0、top_p=1、输出4096、timeout120秒；输入保守上界240000、安全余量8192等维持既有冻结口径，实际执行前重新核对官方可用性，不静默换模型。若确需变更预算，另行版本化并先离线预检。

官方JSON模式要求指定`response_format`并在提示中说明JSON结构；它不能替代本项目的Schema、标识符与语义核验。输出截断、空内容等情况按本项目账目和一次结构修复合同处理，不直接照搬无限重试建议。参考[官方JSON模式](https://api-docs.deepseek.com/guides/json_mode/)与[Chat Completion接口](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 5. 工作包二：补充独立真实训练来源

### 5.1 推荐规模与理由

推荐下一批小试新增**2个独立来源组 × B1/B2两种公开业务配置 × D0采集 = 4个新终止训练episode**。与旧两条合计为3组、6个episode；这只是小试，不替代主规范既定完整训练矩阵，也不构成正式收益实验。

选择两个新组的原因：旧组没有合法父卡；只增加一个组，即使出现两张合法卡，也可能全来自同一新组，仍无法形成跨来源支持。两个新组才提供必要的跨组父卡条件，但四次生成仍可能全部失败。

B1/B2是同源配置变体，不是两个独立来源；四个新episode最多提供两个新独立组。语义支持要求“同一个声明被两个组支持”，并非整个库达到两个组就自动满足。

### 5.2 来源准入与暴露核查

1. 重新读取实际数据、split、暴露登记、旧标注及全部相关实验计划；不能直接使用A0历史候选列表作为可用白名单。
2. 来源审计覆盖根目录及嵌套计划，特别是GEN目录内B1诊断计划，显式登记扫描范围和遗漏风险；避免仅匹配根级`PLAN_*`。
3. 按原订单身份、来源继承、顺序几何与无序几何/质量指纹聚类去重，保留精度规则及冲突报告；相似或同源变体不得分到不同独立组。
4. 先冻结训练/开发与独立验证/测试划分；所有参与协议调试、选样及生成的材料视为已暴露训练/开发。不得拿holdout补足来源门槛。
5. 在观察新运行结果之前，冻结来源选择顺序、B1/B2配置、D0采集方式、终止规则、异常分类和操作清单。预检只用合法公共输入与必要可行性条件，不按成功率或低违规筛选来源。
6. 保存原生Jev真实执行、动作和公共反馈；G0/H0结果、合成轨迹、离线服务替身及同一轨迹复制不作为新教师。

历史筛选中的箱数/尺寸/质量/体积条件只是输入预检，不是可完成性的oracle证明。新来源不足时交付数据缺口，不复用被暴露测试或通过裁剪、增强制造独立来源。

### 5.3 失败与服务截断

保留完整终止记录；规划失败、业务违规、正常结束和服务故障分别统计。服务故障不作为动作质量负例。故障episode的计数、可总结性和频次身份在操作前明确，按共享账目保守处理，不通过重建同一episode获得第二次机会。

先用一个新episode完成协议冻结后的真实冒烟；通过既定技术门槛才执行其余已登记小试。若发现合同错误，停止扩大、保留响应、离线修复版本；不得重发该episode，也不得看到结果后反复换提示追求有效卡。

## 6. 工作包三：生成频次、合并及成本管理

### 6.1 操作账目

继续使用正式共享账目，生成频次身份绑定原始episode而非提示摘要。新协议不能另开空账目重置限额。操作前登记输入、覆盖、提示、模型、版本、原件摘要、预期操作类型及可用频次；发送状态未知时停止自动重试。

四个新增episode最多四次生成、最多八条原始候选。总计六个episode时，按每四个最多一次合并，累计最多一次合并；必须先核对现有实现采用的episode/claim计数与实际合格终止记录是否一致，不通过失败记录或重复预约放大次数。

若满足父卡及兼容条件，本批自然上界为四次生成加一次合并，各最多一次结构修复，即最多十次新增文本请求。这是条件推导的自然上界，不是额外总费用硬上限、必用额度或允许语义重试的授权；若无合并条件则不调用。任何额外文本审核器不包含在此推导中，不能隐式开启。

Jev采集调用数取决于实际决策、故障和原生协议，单独预估并记录，不冒称每个episode固定调用一次。usage、延迟、失败、缓存命中与账单分别统计；未知为null，估算标为估算，不把历史复用计成新增付费。

### 6.2 合并准入与输出

合并父卡必须来自真实合法输出，已完成字段检查并有独立语义审核记录；单源支持的候选可保留候选身份，不能提前激活。选择父卡时检查：公共规则语义兼容、适用范围可交集、单位一致、建议相容、无未解决冲突。不能仅因关键词相似或B1/B2名称相同就合并。

同源父卡可以满足某些工程合并条件，但不能制造跨来源支持。本轮优先审查跨两个新来源组的兼容父卡对；无兼容对则合并N/A，不凑调用。

合并请求显式包含全部父卡原文及其实际请求内证据、反例、未知和覆盖。新卡保留父卡谱系，任何新增结论必须有证据；不能把反例删除后形成泛化建议。新卡内容变化后必须重新审核，父卡accepted不自动继承为新卡accepted。

合并成功也不等于激活成功。父卡是否退役按既有生命周期合同处理，只有替代关系明确且新卡已获准入时才记录退役；所有原件可追溯。

## 7. 工作包四：独立语义支持审核

### 7.1 审核组织

代码负责确定性检查，独立审阅者负责语义判断。候选审核交给具名、未承担该条生成或改写的独立审阅者；争议条目由另一名审阅者裁决，裁决前不进入active。开发代理、生成模型自评、用户批准发送请求均不代替这一环节。

当前审核导入对reviewer名称的检查不等于现实身份认证。实施中须记录实际审阅者、日期、职责独立性声明及协议版本，如没有外部身份系统便明确其为具名声明，不夸大为认证签名。审阅者尚未落实时，可完成工程与材料，但真实semantic_review保持待完成。

### 7.2 每条声明的审核表

| 审核项 | 必须填写的结论/证据 |
|---|---|
| 声明及范围 | 被审核的准确文本、内容摘要、适用条件、排除条件 |
| 逐来源观察 | 每个source group的实际事件、事实槽位、动作、反馈与字段语义 |
| 支持关系 | 对每组分别给出支持/不支持/不确定及理由；不以引用数量代替来源数 |
| 比较依据 | 是真实前后观察、实际对比还是未执行假设；反事实未知明确标注 |
| 反例/未知 | 是否完整保留，是否要求缩小范围，是否存在未解决冲突 |
| 角色 | rule_restatement、current_rule_application或sequential_resource_strategy及理由 |
| 观察与假设 | 是否把checked当满足、把相关当因果、把业务载荷当物理容量 |
| 增量内容 | 相对当前公开规则究竟增加了什么情境或序贯资源信息 |
| 决定 | 接受候选/拒绝/待裁决；active资格另由门槛计算 |

审阅者不能只确认链接“存在且值相等”。必须指出每个来源如何支持建议、条件边界是否一致、反例是否推翻泛化。unknown和deferred不是成功证据；support标签先是生成器提议，经过审核才形成有效支持。

纯规则复述可保留为分类材料，不纳入M0活跃经验；规则应用类也不能未经审核全部当成复述或策略。序贯策略需有可追溯跨步对象和资源变化，单次静态事实不自动支持未来资源收益。

### 7.3 审核后的流转

- 技术检查失败：保留原始建议及拒绝原因，不进入candidate。
- 合法、单源支持、审核接受：保留candidate，等待合规跨来源证据或合并机会。
- 不确定或冲突未决：保留待审/候选状态，禁止注入。
- 至少两组真实语义支持、独立审核接受、非纯规则复述、无未决冲突、范围兼容：进入active资格检查。
- 内容需重写：审阅者可写拒绝/缩小范围建议，但不得直接改成新的成功模型卡；新文本只能来自后续合规生成或合并，并重新核验、审核。

审核文件绑定卡内容、事实表、原始响应、请求、来源清单及协议摘要；改动任一关键内容则旧结论失效。新审核包包含逐来源表、引证导航、拒绝理由、冲突裁决和导入回执。

## 8. 工作包五：真实活跃库与非空M0验收

### 8.1 冻结前门槛

每张卡先满足来源、语义审核和生命周期要求，再按实际渲染正文核对UTF-8预算：单条≤1600、canonical memories数组≤4800、Top3。不能只按advice字段计算，也不能超过预算后手工删反例。活跃卡容量仍≤64，按既有独立支持组数及摘要确定性排序，不引入模型confidence作为可信度。

显式冻结哪些字段注入、哪些只本地审计；比较依据或限制中理解正文必需的部分须在可注入表达中自足。渲染结果与证据附件分别有摘要，索引与正文一致。保存原始生成、映射、审核、谱系、账目、配置和完整manifest；离线加载不读密钥、不联网。

### 8.2 非空验证分两层

**第一层：真实内容的离线工程验收。** 使用真实新冻结包和预先定义的训练/开发状态，经正常query、gates、BM25与预算链路获得至少一次非空M0注入。状态可来自已暴露开发材料，须披露选择规则；不能用独立测试集调检索，也不能以收益挑选展示状态。没有适用状态时如实报告，不强制注入或放松门控。

检查D0/R0/M0共同请求体去除memories后完全一致，物理候选一致；Jev实际请求中的记忆文本逐字等于冻结渲染结果。记录命中、门控排除、预算排除、条数/字节、来源覆盖及文档集中度；运行records、恢复、查看器、安装包加载、迁移和篡改检查。服务替身结果明确标为离线工程，不计真实Jev或收益。

**第二层：真实Jev非空运行与后续效果。** 工程门槛通过后，另按冻结执行计划完成必要最小真实Jev联调，并记录实际请求与Choice。若暂未执行，只能声明“真实卡包离线非空工程通过”，不能声明真实Jev非空运行通过。正式收益比较继续走J4-C独立数据与矩阵。

### 8.3 R0阻塞须单独处理

当前R0为0/24。即使M0后来非空，也不能直接把M0对空R0的差异解释为经验组织收益。

在现有历史投影内做版本化、确定性冗余消除，列出每个删减字段的等价恢复或语义覆盖证明；保留规则、资源、负反馈、动作和必要对象关系，整事件准入，不逐段摘取有利信息。重做训练预检、字段语义对照和B1公平性回归。

若完整语义仍无法装入既定预算，R0对照继续标记不可用；在正式收益实验前冻结合理的实验修订或共同预算校准方案。不得仅放宽R0一臂预算或悄悄改变M0检索条件。R0改进不作为“已经生成合法卡”的替代验收。

## 11. 测试与验收清单

复用现有测试结构，新增测试针对新的失效模式；旧288项结果作为历史基线，不冒充新版本已重跑。代码改动后按受影响模块运行必要测试，再完成安装及真实产物专项核验。

| 编号 | 必测情境 | 通过条件 |
|---|---|---|
| IMP-01 | 同输入重复prepare、字段顺序/版本变化 | 冻结版本内确定性一致，跨版本不混淆 |
| IMP-02 | 对象顺序变化、同尺寸同质量对象、多步出现 | 稳定别名不串物；不能解析则拒绝相应序贯支持；不泄漏未来对象 |
| IMP-03 | 正文含全局ID、候选号或请求内事实编号 | 技术拒绝；合法结构化引用保留，不自动清洗 |
| IMP-04 | 引用本地未发送字段、错误类型/单位/数值、伪造覆盖 | 拒绝；包含布尔与数值等容易混淆类型的反例 |
| IMP-05 | checked/deferred与违规实例的语义fixture | 字典与评价器相符；fixture不冒充真实语义审核 |
| IMP-06 | 同组多episode、多卡、重复导出、来源继承 | 独立组数不增加；两个真实组也必须逐声明确认支持 |
| IMP-07 | 单源accepted、纯复述、冲突、unknown、旧内容review | 均不能越过active门槛；内容变更使审核失效 |
| IMP-08 | 合并同源/跨源、不兼容父卡、遗漏反例、频次不足 | 保留正确谱系，拒绝越界；不靠四个同组episode满足两来源支持 |
| IMP-09 | 换提示/目录/run重新请求旧episode | 复用旧正式响应或拒绝新发，不重置频次 |
| IMP-10 | 发送未知、raw已存后崩溃、解析/导入中断 | 重启不重发；最多一次结构修复，无语义修复 |
| IMP-11 | 总结超限、卡渲染超1600、数组超4800 | 分开报告并拒绝，不暗中逐窗或截断必要语义 |
| IMP-12 | 旧包、新空包、新真实非空包及附件篡改 | 版本严格、迁移可复核，篡改被拒，凭证/网络副作用为0 |
| IMP-13 | 正常检索、门控未知、三臂请求与恢复 | 适用才命中；去掉memories的公共请求一致，日志与实际注入一致 |

## 12. 指标、失败出口与最终交付判定

### 12.1 必须分开统计的指标

| 指标 | 分母/口径 |
|---|---|
| 技术通过率 | 合法候选数/原始建议数；零原始建议时为N/A，不写100% |
| 标识符拒绝率 | 此类拒绝建议数/原始建议数；仅描述本批样本 |
| 引证字段通过率 | 通过的链接数/全部链接数；不命名为语义正确率 |
| 独立审核接受率 | 接受候选数/实际审阅候选数；未审为NOT_RUN |
| 声明支持来源 | 逐卡实际经审阅支持的独立来源集合；反例与未知另列 |
| 活跃库 | active卡数、来源分布、角色分布、预算排除及冲突数 |
| 非空M0 | 非空决策数/全部受测决策；离线和真实Jev分开 |
| R0可注入率 | 可注入完整事件数/全部合格事件数；保留原0/24对照 |
| 真实操作成本 | 新增/复用、生成/修复/合并、成功/失败/未知分别计数，usage与实际/估算费用分开 |

不得把15条字段匹配、两个episode、两张同源卡、审核文件存在或fixture命中作为两来源真实支持。小试描述性指标不能升级为稳定成功率或泛化收益。

### 12.2 预定义失败出口

| 情况 | 处理与交付 |
|---|---|
| 新协议离线检查失败 | 停止真实发送，修复工程并保留诊断 |
| 新来源不足或去重冲突 | 交付来源缺口，训练/测试隔离不变 |
| 新输出仍全部拒绝 | 保留raw及分类原因，交付空库；不重发同episode |
| 有合法候选但不足两组支持 | 保留candidate和独立审核，不激活、不伪造支持 |
| 没有独立审阅者 | 完成审核包与工程，语义验收明确待完成 |
| 无兼容父卡或无合并额度 | merge=N/A或未具备条件，不以合并调用解决数据不足 |
| 有active但无合适检索状态 | 卡库与检索验收分别报告，不强制塞入请求 |
| R0仍为空 | 不开展“组织增量已验证”的结论；另冻结公平对照修订 |
| 服务不可用/发送未知 | 按账目保守恢复，保留服务失败，继续离线可完成工作 |

### 12.3 最终交付清单与结论用语

交付应包含：根因审计、新版本合同与提示、实现和针对性测试、来源/暴露/split清单、真实采集与导出、正式操作账目、全部raw与拒绝、合法候选及谱系、独立语义审核、新冻结manifest、非空或空库统计、安装/恢复/篡改/records/viewer证据、范围明确的最终报告。

按事实分别写结论：

- **协议工程完成**：离线合同、恢复与兼容通过，不等于真实经验成立。
- **真实经验支持成立**：至少一张卡通过两组独立真实支持和独立语义审核，不等于已经有收益。
- **真实非空库运行通过**：明确区分真实内容离线注入与真实Jev实际请求；二者不能互相代替。
- **本轮未建立非空库**：仍可交付合规工程与真实失败记录，明确剩余数据/审核/语义缺口。
- **收益成立**：仅在另行冻结并完成J4-C独立比较后判断，本方案不预设结果。

推荐首先实施P0/P1，并完成P2的来源和审核人选准备；这能减少新真实调用再次全部因接口问题失效的风险。所有后续结果进入新的阶段产出报告，本文继续保留为实施方案。
