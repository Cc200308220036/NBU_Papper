## 1. 项目决定与阶段目标

用户决定暂缓O3补充验证，开发重点转向O4。O3独立来源泛化等事项仍为未验证状态，**不作为O4开发前置条件**。复用已认证的O3数值稳定V2作为工程参照，不重跑相同P0/P1付费矩阵，不改写旧V1 C的FAIL。

O4需要实现：在感知准确、信息完整确定的仿真环境中，将对象属性与组合业务说明编译为确定性约束，在统一物理候选和布局策略下逐箱执行，并独立检查编译质量及整单效果。

新增必做阶段**O4-F：最多3箱待码缓冲与业务约束下的顺序/位置联合规划**。它面向多种业务属性、箱体几何与到货顺序的共同作用，不限定为禁压案例。保留单箱基线，完成O4-C后实施O4-F，再交付覆盖两模式的O4-D真实API实验。F使用独立编号，避免与已有E系列区域/朝向编号混淆。

阶段成功分为三层，分别报告：

1. **工程通过**：协议、执行器、独立评价、回放与数据隔离正确。
2. **能力测量完成**：真实规则编译器、LLM、VLM的成功与失败均有完整记录。
3. **研究假设成立与否**：未见组合、语言泛化或图像增量是否有证据。不得将第1层直接写成第3层，也不得将模型必须优于基线作为工程验收门槛。

## 2. 开发范围与边界

| 内容 | 本阶段要求 |
|---|---|
| 上游感知 | 直接提供准确对象ID、尺寸、质量、位置、属性、标签及所属箱面；不实现检测、OCR、跟踪、标定或属性估计 |
| 信息条件 | 无遮挡、歧义、冲突来源、未知属性、置信度、补拍或主动观察；非法输入作为协议反例，不作为不确定性研究 |
| 在线条件 | 保留`single`单箱模式，新增`buffered`待码缓冲模式，容量最多3箱且包含当前新到箱；仅见已到货信息，不见未来箱体、顺序、参考布局或未来反馈 |
| 动作 | 单箱模式选位；缓冲模式支持等待到货及从待码箱中选箱选位；一次只提交一箱，不让模型产生自由坐标 |
| 首轮朝向 | 沿用直立、yaw 0°/90°；区域及方向作为后续扩展单独验收 |
| 物理模型 | 沿用几何、支撑及载荷传播代理规则；不主张真实损伤预测或动力学稳定性 |
| 业务约束 | 首轮三类硬约束，以及对象集合、条件、例外和明确优先级 |
| 布局 | 单箱固定公共策略；缓冲在相同候选/软预算基础上新增有界联合搜索，独立比较顺序与搜索贡献，不同时调整物理参数 |
| 模型 | 独立O4文本/图像adapter；供应商和模型能力在实际调用前核验，不根据历史名称假定支持图像 |
| 排除项 | O5动态记忆、超过3箱缓冲、已码箱移垛/撤回、多托盘分配、机器人运动规划/控制、真实场景部署 |

O4-A/B/C完成单箱语义基线，O4-F完成通用待码缓冲与联合规划，两者均属于本轮离线开发交付；O4-D为对应模式离线通过后交付用户运行的真实API实验。区域与朝向扩展不阻塞三约束及缓冲交付。

## 3. 预期实现效果：按货物与包装要求完成混合订单

### 3.1 场景与任务定位

以一托盘逐箱到货的混合订单为例，货物可以包含饼干外箱、玻璃杯外箱、小家电外箱与清洁用品外箱。每箱有准确的货物类别、质量、包装处理标记和限载信息，作业单给出本次订单的摆放要求。**首轮取消抽象A/B业务组及`group_id`字段，按具体货物属性和包装要求识别适用对象。** 数据训练/验证划分和实验配对分组仍保留，与货物分类无关。

下述规则是本项目明确设定的仿真作业要求，不代表行业通用规定。食品或玻璃制品的类别本身不自动等于禁压，包装加固也不自动推出承载能力；必须依据公开标签、明确作业说明及独立物理参数。禁止接触仅测直接面接触，不代表已实现卫生隔离、防泄漏或危险品合规。

### 3.2 首轮应看到的具体效果

| 作业要求 | 系统应实现的效果 | 可核对证据 |
|---|---|---|
| “带禁压标记的箱体不得承受顶部载荷” | 有相邻可放位置时不把新箱压在禁压箱上；无可行位置则明确停止；不强制禁压箱一定最后到货 | 禁压对象集合、支撑/间接载荷、被排除候选及终止原因 |
| “普通箱按各自标签限载” | 读取每箱不同阈值，按支撑面积和多层传播核验，不把每一步新增载荷误当累计载荷 | 逐对象限值、before/after累计载荷与差值 |
| “本订单允许食品和清洁用品同托盘，但外箱不得直接面接触” | 按准确货物类别排除相互直接接触的位置；同类箱不因这条规则被排除 | 食品/清洁用品对象集合、直接接触对与允许候选 |
| “已加固且无禁压标记的玻璃制品箱改按订单指定2 kg限载，其余仍按标签” | 只改命中三个条件的对象；普通玻璃箱和其他类别不受该例外影响；有禁压标记的加固箱仍禁压 | 条件展开、例外覆盖范围及2 kg边界案例 |
| “重箱尽量低放、靠近中心” | 在业务硬约束可行集合内执行固定公共软目标，不为居中或低位违反禁压/限载 | 业务可行集合、软预算、最终排序；此项复用基线，不计作新增语言能力 |

不承诺禁压箱总在最顶层、重箱绝对在底层或任意到货流都能放完。单箱基线没有重排能力；O4-F仅重排最多3个已到货待码箱，不能读取未来信息或移动已码箱。两模式都可能提前终止，必须保留该结果。

首轮禁止接触仅筛选共享候选器实际提供的位置，不新增指定毫米间隔、隔板或分托盘动作。没有符合要求的候选时明确停止，不把“禁止接触”展示成已支持自动生成安全间距。

### 3.3 一份完整作业单及预期解释

> 本订单普通箱按各自标签的累计顶部限载执行；带禁压标记的箱体禁止顶部加载。已加固且无禁压标记的玻璃制品外箱，改按订单指定的2 kg业务限载执行，替代其标签业务限载。食品外箱与清洁用品外箱允许同托盘，但不得直接面接触。所有箱体仍须满足独立物理承载限制。

以下是同一作业单在不同箱体上的明确效果，数值为仿真示例：

| 箱体 | 准确事实 | 编译后的业务效果 |
|---|---|---|
| 饼干箱 | 食品、禁压=true、标签限载0 kg | 顶部载荷0 kg；不与清洁用品箱直接面接触 |
| 普通玻璃杯箱 | 玻璃制品、加固=false、禁压=false、标签限载1 kg | 顶部限载1 kg，不套用加固例外 |
| 加固玻璃杯箱 | 玻璃制品、加固=true、禁压=false、标签限载5 kg | 按本订单例外执行2 kg，而非5 kg |
| 禁压玻璃杯箱 | 玻璃制品、加固=true、禁压=true、标签限载0 kg | 仍禁压，不能因“已加固”取消禁压 |
| 小家电箱 | 电子产品、加固=true、禁压=false、标签限载8 kg | 限载8 kg，不套用玻璃制品例外 |
| 清洁用品箱 | 清洁用品、禁压=false、标签限载6 kg | 限载6 kg；不与食品箱直接面接触 |

程序应在每次到货时重新展开这些属性条件，输出可检查AST并核验当前箱与全部受影响已有箱体。食品先到或清洁用品先到，接触规则含义相同。用本方法编译结果选候选，隐藏参考事后评价；错误编译及提前终止如实保留，实际提交始终接受独立物理检查。

无物理候选、编译后无业务可行候选、非法AST和API失败分别记录。规则改变不一定改变动作：先比较规则语义与允许候选，再核对有决策机会时的动作变化。

### 3.4 后续扩展应看到的效果

首轮通过后，区域/朝向扩展用于实现具体作业要求，例如“指定货物底面完全放在公共标记区域内”“标签朝向指定托盘外侧以便核对”。明确先由仿真给出区域、箱面和目标方向，再编译约束；尚未开发这些能力时，不把演示图中的合理布局写成已支持区域或标签朝外。

### 3.5 待码缓冲应实现的通用效果

| 业务与几何背景 | 需要实现的行为 |
|---|---|
| 禁压、逐箱限载与可用支撑共同影响布局 | 可暂存当前箱，待其他箱到货后比较多种码放顺序；不硬编码禁压箱最后放 |
| 大小箱在同一空间内存在填充或支撑取舍 | 联合比较顺序与位置，不固定大箱先放、重箱先放或底层必须先铺满 |
| 禁止接触、标签限载和包装例外同时生效 | 在模拟每次放置时重新检查全部适用规则，不以暂存取消业务限制 |
| 某箱暂不可放但另一箱可放 | 选择可放箱并重新分析剩余箱，不能只检查队首就宣布全部无解 |
| 缓冲满、尾单不足3箱或全部箱仍不可放 | 不接收第4箱；到货结束后处理余箱，必要时明确终止并保留待码箱 |

交付至少展示一条“暂存→等待→选择另一箱→提交→重规划→处理余箱”的完整事件轨迹，也保留无需等待、无收益和仍失败的对照。缓冲收益属于动作空间与规划能力，不能自动归因于模型语义编译。

## 4. 属性与规则的首轮契约

### 4.1 对象观测

保留已有几何与质量字段，新增O4属性侧表，通过准确实例ID关联。拟定字段如下：

| 字段 | 类型与约束 | 用途 |
|---|---|---|
| `object_id` | 非空、场景内唯一字符串；一对一映射原`item_id` | 编译对象引用与日志关联 |
| `cargo_category` | 必填枚举：`food`、`glassware`、`electronics`、`household_cleaner`、`general` | O4仿真货物类别，分别对应食品、玻璃制品、电子产品、清洁用品和其他；仅表示类别，不内置业务禁令 |
| `packaging.reinforced` | 必填boolean | 准确包装加固事实；只有明确作业要求才产生例外，不据此推算物理承载 |
| `labels.no_top_load` | 必填boolean | 准确禁压标签事实 |
| `labels.max_top_load_kg` | 必填、有限且非负数值 | 逐对象标签业务限载；即使禁压为true也保留字段，不默认缺失为无限 |
| `physical_top_load_limit_kg` | 必填、有限且非负；映射已有物理承载值 | 物理候选过滤，与业务限载独立 |
| `fragile`、`weight_class` | 复用已有明确属性及其定义 | 条件筛选及固定重箱软目标；易碎不自动等同于禁压 |
| `mass_kg`、尺寸、位姿 | 沿用原数据单位与坐标约定 | 物理计算及公共事实 |

标签图像与结构化标签事实必须一致。首轮离线核心可先不接图像，但交付VLM对照前必须补齐从公共事实确定性渲染的图像、渲染版本与哈希。

原V1的`product_category`目前主要为`electronics/general`，不能声称已有上述五类货物数据。`cargo_category`在O4独立侧表中确定性派生，来源标记为仿真，不改写原V1类别。旧类别不进入首轮O4选择字段，避免两个分类口径混用；原电子产品映射O4电子产品，其余原general对象再派生其他类别。加固与标签限载均为准确提供的仿真事实，不从名称或图像猜测，也不声称来自真实包装测量。

物理承载侧表值必须与原几何引擎实际使用值一致。首轮不改变物理材料模型，不将禁压标签直接写回旧`stackable`字段来预先过滤业务答案。

### 4.2 三类硬约束的确定语义

| 规则 | 定义 | 必须覆盖的边界 |
|---|---|---|
| `no_top_load` | 目标对象承受的累计顶部载荷不得大于载荷容差，等价业务限载0 kg | 直接及间接加载；地面自身质量不计为顶部载荷 |
| `max_top_load` | 目标对象累计顶部载荷≤规则限值；限值可为常数或该目标的准确标签值 | 多层传播、多支撑面积分摊、等于阈值、超出阈值 |
| `forbidden_contact` | 左右对象集合之间禁止直接面接触，关系对称，排除自身配对 | 水平与垂直面接触均计；边/点接触不计；不将间接支撑当直接接触 |

物理限载与业务限载分别检查；业务限制不能放宽物理上限。底层载荷按支撑面积分摊并逐层传播，不使用“上方所有箱质量简单求和”替代。

首轮固定物理几何容差沿用现有独立检查定义；O4业务载荷容差明确为`1e-6 kg`、面接触容差为`1e-6 mm`。布局数值同分精度使用V2的`1e-12`，三者用途不同，不相互替代，不以扩大容差掩盖动作差异。

### 4.3 集合、条件、例外与优先级

首轮选择表达式仅支持：`all`、`object_ids`、属性`eq`、数值`lt/le/gt/ge`、`and/or/not`。字段路径必须白名单化；表达式树最大深度4，每规则对象ID最多64个。单位统一kg/mm，不接受任意Python表达式、代码执行或模糊匹配。

- 选择表达式保留为符号条件，每步在当前与已到货对象中展开；不能仅在首箱把规则固化为当时存在的ID集合。
- 对象ID规则只允许引用当前及已到货ID。后续到货对象通过属性规则适用，不向选择器公开未来ID。
- 首轮条件是明确的逐对象属性谓词；任意跨对象量词、时序逻辑、动态政策切换不在首轮范围。
- 例外用显式`overrides`规则引用表达；业务说明必须明确例外对象、替代规则及被覆盖范围。
- `priority`数值越小优先级越高；覆盖关系必须指向较低优先级规则，禁止环、自引用和未知规则引用。
- 覆盖仅在相同对象、相同约束族及声明范围内生效。禁止用限载例外取消不相关的禁止接触规则；首轮接触例外通过左右集合排除表达。
- 无显式覆盖的多条限载规则同时生效，等价取较严限值；条件不适用的规则不参与。硬约束不能被布局软目标抵消。
- 同优先级矛盾且无法按上述合取语义解释的要求不进入正常任务集；专门作为非法配置反例，明确拒绝，不静默猜测。

复用范围：数据只读仓库、现有物理候选器、状态提交、独立物理检查、日志与哈希机制。新增O4 schema、编译、业务执行与评价；不得扩写旧V2 schema后仍标识旧版本。

首轮固定采用`relaxed_geometry`的**排序原则**：先依本方法O4 AST求业务可行集合，再按固定重箱低位/居中软目标及其预算进行排序，最终用稳定几何分和Cxx破同分。固定软目标顺序为`heavy_low → heavy_center`，预算分别0.05/0.25；不把软目标语言理解同时加入首轮变量。

原V2选择器绑定旧政策评价器，不能原样调用后宣称支持O4。需要O4 adapter在新可行集合内构建严格软目标锚点、形成同预算允许集合，再执行几何排序；无适用重箱时对应软目标为N/A。参数、锚点、允许集合与排序版本全部写入trace。旧模块不改动，新增适配应有等价回归证明。

只实现安全业务模式，不接入观察模式最小伤害回退。单箱按本方法AST无可行候选即停止；缓冲先检查全部待码箱及接收权限，不因其中一箱无解立即终止，事件规则见第9节O4-F。参考评价器不得拦截本方法的业务误判；物理独立检查始终保留。

## 6. 输入、AST及接口契约

### 6.1 编译请求与响应

编译输入为白名单公共观测、完整业务文本与可选公共图像；首轮不把候选评分、允许候选或候选业务诊断输入编译器，以隔离业务编译能力。

请求至少包含：`schema_version`、`request_id`、`state_hash`、`observation_digest`、`instruction_digest`、坐标及单位声明、当前与已到货对象事实、`instruction_text`、可选图像清单及哈希。

响应至少包含：对应版本与全部绑定字段、`policy_ast`。使用封闭schema，拒绝未知字段、NaN/Inf、负限载、未知属性及越界表达式。首轮绑定版本拟为`o4_request_v1`、`o4_policy_v1`和`o4_response_v1`，实现时冻结。

公共观测含全局业务文本，但不能因此展开未到货属性或对象。私有订单总数可用于事后评价分母，不进入模型提示。

缓冲模式另用拟定`o4_buffer_request_v1`、`o4_buffer_state_v1`、`o4_buffer_action_v1`封闭契约，编译AST仍用`o4_policy_v1`。编译响应增加`buffer_state_hash`绑定，不伪装成旧单箱请求。公共观测包含全部已到货待码箱事实及槽位，但待码箱不提供虚构托盘位姿、不进入支撑计算；模型不输出WAIT或选箱动作，WAIT由冻结接收策略控制、选箱选位由确定性规划器完成。

      "priority": 10,

    },
    {
      "rule_id": "r3",
      "type": "max_top_load",
      "target": {"and": [
        {"eq": {"field": "cargo_category", "value": "glassware"}},
        {"eq": {"field": "packaging.reinforced", "value": true}},

### 6.3 逻辑接口

| 接口 | 输入→输出 | 约束 |
|---|---|---|
| `build_observation` | 当前状态、已到货属性→公共观测 | 不接收参考AST或未来状态 |
| `compile_policy` | 公共请求、编译backend→响应或明确失败 | 不接受评价器提供的答案；backend可为规则/LLM/VLM |
| `validate_and_normalize` | 响应、公共请求→规范AST或错误码 | 仅检查可知结构、引用及一致性，不借隐藏真值补规则 |
| `evaluate_candidates` | 本方法AST、当前状态、物理候选→业务允许集合及trace | 不读取私有参考 |
| `select_and_commit` | 允许集合、公共软目标/预算→提议、物理复核、状态 | 无可行候选停止，不隐式回退到Parser/Oracle |
| `audit_reference` | 私有参考、公共状态、原始提议/提交→评价记录 | 事后运行；不返回供主方法选址的反馈 |
| `receive_next` | 有空槽的真实缓冲状态→新到货或EOS事件 | 仅环境读取下一条私有流；规划器无权查看迭代器后续内容 |
| `generate_buffer_candidates` | 真实/模拟托盘、已到货待码箱→带箱ID的联合候选 | 每箱独立生成，待码箱不充当支撑 |
| `plan_buffer` | 公共缓冲状态、本方法AST、固定预算→首动作及模拟trace | 只模拟已知箱，不提交真实状态、不调用模型 |
| `commit_buffer_action` | 全状态绑定的PLACE→物理复核、托盘与待码原子更新 | 不推进到货，不删失败箱，不执行过期缓存路径 |

语法合法但遗漏规则通常无法在运行时可靠识别。遗漏必须由离线独立参考计为语义错误，不能声称仅靠JSON校验已保证规则完整。

格式修复最多1次，修复提示只含公共原请求与结构/绑定错误，不提供参考AST、正确候选或私有语义差异。合法但语义错误的AST原样进入执行与评价，不用隐藏答案进行修复。

## 7. 数据构建与划分

### 7.1 数据来源与保护

- 只读复用V1订单几何、质量和到货流，O4属性及任务写入新目录；不重建或覆盖原数据集。
- 每条属性保存生成种子、源场景哈希、属性配置版本和对应对象映射。

## 8. 独立评价与失败归因

执行器与参考评价器不能共享“最终业务违规/可行性判定”函数，以免同一个错误自证正确。允许共享底层无业务几何工具，但必须由独立手工金标准核验接触、载荷和例外语义；参考不得照抄模型AST作为答案。

在同一前状态和同一物理候选集合上计算：方法允许集合M、参考允许集合R。集合差异以候选指纹或该次请求绑定的Cxx比较，不跨状态直接比较Cxx。

| 指标 | 定义与分母 |
|---|---|
| 首答/最终有效AST率 | 通过结构及公共语义校验的首次/最终响应数÷全部计划编译任务数；未调用、失败和预算中止保留 |
| 完整规则语义正确率 | 全部规则、对象、阈值、条件及覆盖含义正确数÷全部计划编译任务数；不能用原始JSON相等替代 |
| 对象集合正确率 | 逐规则匹配后的适用对象集合完全正确比例；无效编译计错误，空集合单列 |
| 条件/例外/优先级正确率 | 对应适用任务的正确比例，报告明确分母；同时报告完整任务正确率 |
| 允许集合完全一致率 | M=R的任务比例；另报错误放行M−R、错误拒绝R−M及集合大小 |
| 原始提议参考违规 | 在真实前状态下按参考重算原始动作违规；与屏障/物理拒绝后的提交分开 |
| 完成率 | 全部放完的任务数÷计划完整订单数 |
| 无违规完成率 | 全部放完且最终参考业务违规为0的任务数÷计划完整订单数 |
| 件数/体积比例 | 逐任务已放÷订单总量，再报告任务平均；未开始任务为0 |
| 业务违规 | 新增/加重违规步、最终违规实例、曾违规任务分别报告；违规步率分母为提交步数，无提交为N/A |
| 物理违规 | 提交后独立检查违规数，工程门槛为0；被拒物理提议另计 |
| API指标 | 真实尝试、修复、重试、失败、输入/输出token、P50/P95时延；有核验计价依据才写金额，否则null |

完整语义评价同时使用规则规范化比对和有限声明域上的独立反例检查；阈值等未在当前状态触发的差异仍算规则错误。只有当前动作一致不能证明完整AST语义正确。

失败按层分开：

1. 输入/协议错误：`invalid_observation`、`invalid_binding`、`invalid_ast`、`unsupported_construct`。
2. 服务错误：`provider_error`、`timeout`、`api_budget_exhausted`。
3. 在线终止：`no_physical_candidate`、`no_compiled_business_candidate`、`physical_rejection`、`all_items_placed`。
4. 事后归因：规则遗漏/对象错误/条件错误/覆盖错误/限值错误；Top-K内参考无解但全枚举有解；当前枚举空间参考无解；布局轨迹限制。

参考在同一状态无可行项，只说明该状态、该候选范围的限制，不构成整单全局无解证明。主方法与Oracle闭环进入不同状态后，不直接把两者候选集合做同状态比较。

#### F.2 暂存状态与事件契约

“记录”必须表示箱体仍在可取的待码区，不能仅保留属性后让箱体从物理流程消失。仿真假定最多3个独立暂存槽，每槽一箱、不相互堆叠，均可直接取用；暂存区几何摆放、机械臂取料可达性和真实搬运时延不在首轮范围。

公共状态至少新增：`mode`、`buffer_capacity`、`pending_items`（对象ID、准确事实、到货序号及槽位）、`event_index`、`arrival_count`、`placed_count`、已实际收到的`end_of_stream`。保留独立物理状态哈希，并新增`buffer_state_hash`绑定托盘、待码集合与槽位、容量、事件及EOS；响应另绑定`instruction_digest`。不能仅沿用旧物理哈希，否则相同托盘不同待码区会错误复用动作。

逐事件必须满足：`已到货ID集合 = 已码ID集合 ⊎ 待码ID集合`，二者不交且无重复；待码数≤容量；PLACE不推进到货序号，WAIT不改变托盘；任何箱只能实际提交一次。未到货、已码、未知箱不可取；失败任务的剩余箱保留在结算记录。不能通过移出待码集合制造成功。

动作分为：

- `WAIT_NEXT`：仅在有空槽且尚未收到EOS时请求下一次到货。调用环境后才得知新箱或EOS，绝不事先读取下一箱信息。WAIT不保证一定有下一箱，也不表示使用真实时间睡眠。
- `PLACE`：携带待码`pick_item_id`及绑定的候选标签；通过本方法业务筛选和独立物理检查后，原子提交一箱、释放槽位并更新状态。失败时不能删箱。

环境在最后一箱实际到达时可同时返回EOS，或在下一次合法请求中返回EOS，首轮固定其中一种并写入配置。不得通过公开私有订单总数提前推断EOS；测试两种边界，正式矩阵选定后不混用。

暂存不被当作一次成功放置，WAIT不计提交步。对有限N箱流，正常运行成功接收N次、PLACE至多N次、空读EOS至多1次；有限终止由事件状态机保证，不依赖不断重复WAIT的超时兜底。没有真实到货时间模型时，暂不设置会暗中改变业务优先级的分钟级等待期限。

首轮接收策略固定为`fill_then_plan`：有空槽且未EOS则接收，满容量或EOS后才规划；成功放一箱后再次补充至容量或EOS，再重新规划。缓冲FIFO、启发式和搜索共用此策略。因此首轮等待并非模型根据某一种属性触发；业务属性决定缓冲内如何选箱选位。可提前放置的自适应等待策略后续独立版本开发，不混入首轮收益。

满容量时禁止WAIT；EOS后禁止WAIT，即使尾单仅1/2箱也立即处理。所有待码箱均无物理候选时记录`buffer_no_physical_action`；存在物理候选但本方法AST对所有箱均无业务可行项时记录`buffer_no_compiled_business_action`。仅一箱无解不终止其他箱的尝试。队首FIFO不能放但其他箱能放时，FIFO记录`fifo_head_blocked`，与联合规划的全集合无解区分。

#### F.3 多箱候选与有限联合搜索

复用单箱生成器时，为每个待码箱构造仅含该箱的临时`available_items`，托盘保持相同。临时请求不推进真实到货、事件或状态，也不把其他待码箱当成已码支撑。每箱最多16个候选，容量3时首层原始联合动作最多48个；Top-K=16是**每箱**上限，不是三箱合计16。

候选标签在一次联合请求内唯一，映射必须同时绑定箱ID、候选指纹和全状态哈希，不得把不同箱的C01混作同一动作。输入重排后使用稳定到货序号和候选规范排序，保证容器存储顺序不改变结果。

模拟节点先用当前方法AST检查业务规则，再在每个箱的可行集合内计算第5节同预算允许集合；仅在允许集合中展开。所有模拟后状态重算支撑、间接载荷、接触及对象条件，不只检查新箱自身。业务编译器只在真实公共状态上工作，搜索树内部不追加模型调用、不接收隐藏参考、不伪造新到货。

首轮默认参数为：`search_depth=3`（实际取待码数与深度较小值）、`beam_width=8`、`max_successor_evaluations=256`，每次真实规划重新计数。一次后继评价指尝试一个具体“箱＋位姿”的模拟转移，计数包含被业务/物理检查拒绝的尝试；同状态候选缓存不得隐瞒真实评价次数。最多6种顺序不等于只有6个布局，需同时报告候选分支。

首轮搜索按逐层束搜索实现；确定性展开顺序、同分精度和裁剪规则冻结。达到256次后停止扩展，在已验证可行路径中选择最佳路径；记录`search_truncated=true`及原因，不宣称穷举最优。搜索前缓存各箱公共几何首选动作所需的合法性评价也计入预算，至少保留首层合法动作；若预算配置不足以完成基本首层检查，运行前拒绝配置。候选生成自身枚举耗时另计，不称为被256限制的全部计算量。

叶节点用以下词典序评分，仅比较当前已到货缓冲集合：

1. 模拟中合法放置的件数，越多越优。
2. 模拟已放体积÷搜索开始时待码总体积，越高越优。
3. 叶状态中剩余待码箱具有至少一个本方法业务可行候选的箱数，越多越优。
4. 暴露可堆叠顶面面积÷托盘底面积，越大越优；随后按最大垛高÷允许高度，越低越优。
5. 路径的到货序号与候选指纹序列按字典序破同分。

第3项的候选评价同样计入256预算；未完整计算时标记未知，该层比较统一跳过，不能把“未计算”当0或按缺失值奖励某路径。第4项面积只作代理，不等于完整连续支撑；使用第8节独立物理核验确定实际合法性。评分连续层用固定最大值锚定`1e-12`同分，离散件数不使用容差。评分与预算仅在开发集调整，配置冻结后才运行比较矩阵。

实际只提交最佳路径第一箱，提交后丢弃旧路径并依据新状态重规划；不得跨越实际到货后仍执行旧缓存序列。搜索仅优化当前缓冲可见范围，不预测真实未来箱，不声称整单全局最优。

#### F.4 对照矩阵、业务覆盖与效果证据

先使用独立Oracle AST固定语义，比较以下四种规划器；Oracle是特权语义参考，不是全局最优规划器：

| 方法 | 配置 | 要分离的贡献 |
|---|---|---|
| `single_greedy` | 容量1，原O4-C单箱选位 | 即到即放基线 |
| `buffer_fifo` | 容量3，fill_then_plan，严格到货顺序＋同一单箱选位 | 接收/缓存链路控制；不发生重排 |
| `buffer_heuristic` | 容量3，同一接收策略；先按每箱业务可行候选数升序，再按质量降序、到货序号升序选箱，箱内沿用单箱选位 | 冻结的简单重排基线；无候选箱暂跳过，不硬编码禁压/类别顺序 |
| `buffer_search` | 容量3，同一接收策略与候选/业务/软预算，有界联合搜索 | 多步顺序与位置联合规划 |

增加至少24个缓冲状态机/规划金标准（含正反例），覆盖到货、容量、选箱、EOS、错误及搜索边界。另增加至少12个业务与几何构造案例，四类各3例：承载/禁压与支撑、不同尺寸填充、接触限制、条件/例外组合。构造案例附完整候选和独立期望，不能全部来自同一个“禁压箱先到”模板。

12例中预先指定至少4例“决策机会”案例，每类至少1例：有明确合法的重排序列，与到货顺序存在不同可放进度或最终布局。验收要求搜索复现指定的合法改序，并至少在其中2例比单箱多放箱或恢复完整无违规完成，其余机会例可表现为允许动作/布局改善；正例采用小规模独立穷举验证并控制在默认搜索预算内。另保留至少4例无收益或仍无解，不能用只展示正例证明总体提升。构造案例效果门槛属于功能验证，不推导真实订单平均收益。

### O4-D：真实模型对照与能力评估

前置：单箱要求O4-A/B/C通过，缓冲额外要求O4-F通过；本轮完整交付覆盖两模式。公共图像已验收，真实客户端能力经运行核验。由用户运行真实API，开发者先交付可审查的配置、计划和调用预算。

真实API比较先固定同一个规划器，测规则/LLM/VLM语义差异，再固定编译来源比较单箱/缓冲，避免同时更换模型、容量和搜索后只报告整体提升。搜索树不重复调用模型；真实状态、待码事实或指令发生变化后按绑定协议更新编译请求，WAIT接收事件与API尝试分开记账。

比较四种方法：强规则编译器＋Planner、准确文本事实＋LLM＋Planner、同事实同文本加图像＋VLM＋Planner、Oracle AST＋Planner。图像消融优先使用同一支持图像的模型和相同参数，仅移除图像；跨模型Text/Visual差异不能单独归因于视觉。

先运行至少12条预先选择的编译冒烟任务，覆盖三原语、条件和例外、正负边界；不得按冒烟优劣重选正式样本。随后在冻结的开发矩阵完成真实固定题与在线对照，再按另行冻结的未见测试协议评估泛化。

工程验收要求：

- D1：计划内每次编译/episode都有响应或明确失败记录；原始请求响应与调用账目100%对应，失败和未完成保留。
- D2：不存在测试替身、旧响应冒充新调用、失败后Parser/Oracle兜底或答案修复；首答与修复后结果分别统计。
- D3：公开事实在文本与图像方法间一致；输入泄漏数、已提交物理违规数均为0，实际业务误判不被评价器隐藏。
- D4：所有保存结果可在不联网、不改原始文件的情况下回放；真实随机性以独立调用记录，不用离线重放充当重复实验。
- D5：完整报告有效AST、规则语义、对象集合、条件/例外、允许集合、整单结果及API指标，均可从原始记录重算。
- D6：API预算触发或服务失败造成任务未执行时标记`PARTIAL/FAIL`，不能写完整远程PASS；模型语义错误本身作为测量结果，不改写或删除。

本规范不预设模型准确率、模型优于Parser或视觉收益阈值。真实可靠性目标、正式test重复次数和效应判据须在查看相应测试结果前冻结；模型持平或落后也属于有效研究结果。

## 10. 区域与朝向扩展的独立范围

首轮通过后按以下顺序增加，每项需新schema版本或明确能力版本、对应基线和独立验收：

| 扩展 | 新增内容 | 验收重点 |
|---|---|---|
| O4-E1区域 | `inside_region`，区域边界由仿真公共给定 | 明确要求整个底面在区域内，边界含容差；不能只检查箱体中心 |
| O4-E2相对位置 | 明确坐标系下的left/right等声明关系 | 明确按包围盒完全分离还是中心比较，首个实现仅选一种并冻结；交换对象/坐标方向的反例正确 |
| O4-E3允许朝向 | `allowed_yaw`，支持0/90/180/270 | 0/180尺寸一致、90/270尺寸一致；候选、物理检查、状态哈希和回放全部支持 |
| O4-E4标签朝外 | 准确本地箱面、位姿变换、显式外向方向或目标托盘边 | 冻结“朝外”的几何定义，正确变换法向；保留同几何不同标签朝向候选，文本基线同步获得事实 |

不把“所有箱始终直立”下恒满足的此面向上约束单独算作动作能力提升。任何扩展都不能只在schema新增字段而执行器忽略。

## 11. 产物、配置及运行交付

每次运行使用不存在的新目录，建议位于`semantic_pallet_planner/outputs/EXP_O4_<阶段>_<日期>_<序号>/`。配置、代码及数据摘要必须先于模型调用写入并冻结。

必需产物：

```text
manifest.json                  阶段、方法、种子、源码/数据/模型/提示版本
config.snapshot.json           属性、规则、布局、容差、API预算与参数
plan.json                      计划任务、配对组、来源组与运行分母
public/                        公共请求、图像及哈希
private/                       参考规则、映射和同状态参考评价
responses/                     首答/修复原始响应、解析结果与错误
episodes/                      before/after、候选、提议/提交和终止日志
metrics/                       编译、候选、完整订单及逐来源指标
audit/                         泄漏、划分、保护文件、调用账目与篡改检查
replay_report.json
acceptance_report.json
README.md                      实际命令、环境、结果、未结项及复现说明
```

缓冲额外保存`events.jsonl`（接收/WAIT/PLACE/EOS及前后全状态）、`buffer_search_trace.jsonl`（模拟路径、预算、裁剪和首动作）、`metrics/buffer_per_episode.csv`、`audit/buffer_conservation.json`及`buffer_acceptance.json`。manifest显式区分容量、接收策略、规划器、编译backend、候选/评分/搜索版本；episode不得仅按场景名命名而覆盖其他模式。

真实API原始响应中的敏感凭据不得落盘；usage缺失需记录，费用未知保留null。公开发布产物与内部审计原件分开，不能因发布删字段而破坏内部证据。

CLI应支持数据构建/校验、固定题、在线订单、离线验收和只读回放；新增模式、容量、接收策略、缓冲规划器及搜索预算参数，非法组合启动前拒绝。远程模式显式开启，API预算必填，输出目录拒绝覆盖。**本文不提供尚未实现的命令示例**；开发交付时必须附实际`--help`、单箱/缓冲最小离线命令及经对应模式离线验收后的用户API指令。

## 12. 实施顺序与最终交付清单

推荐按依赖顺序开发：

1. 冻结三类规则、属性、容差和例外语义，完成36个独立金标准的期望值。
2. 实现O4观测/AST schema与属性数据派生、公共/私有隔离，验收O4-A核心。
3. 实现规则编译器、规范化和独立业务评价，验收O4-B。
4. 实现O4候选执行与固定布局adapter，完成配对与完整订单、回放，验收O4-C。
5. 完成O4-F待码区、事件/绑定协议、多箱候选及三种缓冲规划器，固定Oracle语义完成跨业务构造案例与四方法矩阵，再复核强规则语义一致性。
6. 完成公共图像、文本/图像adapter及模拟传输测试，交付单箱/缓冲真实API配置与手册。
7. 用户执行O4-D，分别分析编译错误、缓冲规划收益、候选限制及图像增量，不混淆归因。
8. 根据结果再开展区域、相对位置和朝向扩展；O3独立验证与O5经验继续保留为独立待办。

阶段报告必须明确：本次实现了哪些规则、属性和组合；哪些只是schema占位；哪些测试通过；真实API是否执行；是否使用测试替身；多少来源和多少依赖任务；哪些无解/失败；未见泛化和视觉增量是否实际得到证据。

本轮开发的完成定义是：**O4-A/B/C/F门槛逐项通过，并交付单箱与最多3箱缓冲模式的真实API可运行入口。** 仅完成A/B/C时标记“单箱开发完成、缓冲F待完成”，不能宣称整轮O4开发完成。O4-D及E系列单独标记状态，不将其未执行伪装为已验证；自然订单上的缓冲收益仍须由比较结果证明。
