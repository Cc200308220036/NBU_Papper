## 2. 目标、非目标和不可变条件

### 2.1 S2总体目标

在冻结的开发集前8个完整订单上，以同一物理环境运行G0和真实图文D0，确认：模型请求实际包含并正确传输两张图；候选/状态/响应/提交可追溯；失败、费用和未知请求可审计；任务难度得到如实诊断。通过后独立封存D0行为契约，供S3训练轨迹采集使用。

**本阶段不要求D0胜过G0，也不要求8单全部装完。** 工程通过、实验有效性、任务难度和装载表现分别判定。

### 2.2 允许开发与禁止扩展

允许新增O5专用模块和测试，必要时修改活动O5代码及专用runner；每项修改须记录差异并建立新计划。原S1代码快照、数据、计划、结果、红测试及验收原件不得覆盖。

不修改原E2候选、共享评分、原默认A、物理oracle、ReMe vendor或O4/B0历史证据。不开发AST、搜索/beam、未来箱预演、正确动作提示、人工策略、R0/M0、经验卡或训练采集入口。不读取训练/测试任务用于模型调试，不把pilot日志写入经验库。

### 2.3 必须保持的环境与行为

- 固定原A/E2物理候选后端，regions=[]、单箱缓冲1、Top-K≤16、yaw 0/90°，容器与载荷、支撑/传播承重等原物理规则不变。
- 只公开当前箱与已放状态；不发送来源ID、split、完整订单长度/分母、后续箱、私有评分、原G分/排序、AST、参考布局或方法成绩。
- 公共JSON、两张PNG、Cxx映射和state_hash绑定；同公共状态生成相同物理池和显示映射规则。方法走向不同状态后不要求其候选逐条相同。
- 输出仅允许绑定的PLACE/STOP；不接受自由坐标、代码或属性改写。选中候选通过独立物理检查后才提交。
- 非空决策最多两次尝试：原始请求一次，只有格式/绑定错误允许一次修复。服务错误不转换为格式修复，不自动换模型、换候选或使用G0兜底。
- 空候选直接停止，不调用模型。主动STOP、非法输出、物理拒绝、服务失败和预算中断均保留完整订单分母。
- 每个决策新上下文；不使用跨订单聊天、previous-response链、服务端可写会话或隐式摘要。修复仅反馈允许的错误码，不追加策略解释。

## 3. 目标模式拆分与阶段门槛

建议按下表独立设目标。前一目标完成不自动授权后一目标的远程支出。

|子阶段|具体目标|完成状态|停止/阻塞条件|
|---|---|---|---|
|S2-A 离线接入工程|完成远程契约、provider适配、费用预留、状态恢复、计划生成、只读复核和离线测试；输出可审查预检/调用计划|`READY_FOR_AUTHORIZED_PREFLIGHT`，真实调用0|缺provider信息时保留待填字段，远程准入明确BLOCKED；不虚构模型或价格，不将草案写成可执行|
|S2-B 真实预检与pilot计划冻结|在明确授权和小额上限内验证真实接口、PNG传输、模型/参数、usage及计价，冻结8单计划|`READY_FOR_AUTHORIZED_PILOT`|图片不支持、计价不能约束、协议冲突、未知请求或凭据不可用时停止；保留已花费用|
|S2-C 8单pilot与D0封存|按已批准具体计划运行，复核16条订单记录，评估难度和工程门槛，封存D0或交付HOLD/INVALID|`PASS_D0_FROZEN`、`HOLD_DIFFICULTY`、`HOLD_ENGINEERING`、`INVALID_OR_PARTIAL`之一|不得通过换单、无限重跑、放宽门槛或训练经验来完成目标|

S2-A可以在没有远程支出授权时开发完成，但其完成不代表S2全阶段通过。S2-B涉及真实API，即使只有一次探针也需要纳入具体授权。S2-C要求授权覆盖该冻结计划、阶段金额与账户；已明确覆盖的内容无需反复询问。

模型/provider尚未指定时，可先实现与provider解耦的内部契约和可注入的HTTP适配测试；真实参数映射必须在选定接口后核实，不能默认所有“兼容”服务语义相同。

## 4. 工作包与实现要求

以下模块名为建议，最终可合并，但各项职责、证据和验收不能省略。

### W0 启动盘点与保护

1. 记录当前HEAD、全部未提交修改、实际import路径、依赖、S1证据和本规范哈希。当前工作区已有S1未提交文件，禁止reset/clean或覆盖这些成果。
2. 对O4/B0封存文件、原E2、共享评分、物理配置、vendor和S1原件建立保护清单；对允许修改的活动O5源码建立单独变更清单。不能要求S2新增代码后全源码与S1摘要仍相同，也不能删除旧快照以绕过漂移检查。
3. 锁定DATA03和既有规则计划，核验140簇数据manifest、文件摘要与前8个开发任务。禁止按离线/真实成绩重排或换单。
4. 不复跑旧D-L3、D replay、旧240条额外复查或其他历史搜索实验。

**交付：** `startup_audit.json`、`protected_files.json`、基线变更清单、数据及任务摘要。

### W1 远程契约与provider适配

建议新增 `o5/remote_config.py`、`o5/remote_transport.py`，或同职责文件。

- 计划中固定provider、endpoint标识、精确模型请求名、可固定快照/别名限制、SDK/HTTP版本、timeout、采样参数、seed能力、输出上限、图像格式/detail、响应提取规则。
- provider差异只影响传输层。发送的语义公共请求、基础目标、候选、图片和一次修复规则不能因provider而改变。若接口无法实现同一契约，报告冲突并另立版本。
- 返回内部结果至少包含原始HTTP/服务状态、provider_request_id、返回model/版本元数据、finish_reason、原始响应正文或受控保存位置、选择文本、usage、耗时、计费信息及缺失标记。
- 保留模型原始输出；不通过另一个模型清洗、不补候选、不补request_id/state_hash，不在SDK中偷偷修复JSON。拒绝、截断、空响应、非文本/非预期tool输出按冻结规则归类。
- SDK、代理与HTTP层自动重试均显式关闭并测试。每个实际发出的模型请求必须对应一条attempt；transport不能在一次complete中自行重发。
- 仅从环境变量或既有凭据机制读取密钥，不写入计划、源码、HTTP header快照、异常或报告。记录账户的非敏感标识用于预算关联；日志脱敏不删除计费/响应绑定证据。
- S1离线命令继续受socket guard保护；S2远程入口必须显式区分，无法通过 `stub_policy` 或单个布尔值把离线结果重命名为真实实验。

### W2 图文、输入上限与真实预检

- 发送前校验公共schema、图片SHA/尺寸/类型、显示映射与状态绑定；构造最终provider body后记录其脱敏摘要和两个图片字节摘要。
- 记录图片编码方式、detail、实际尺寸和是否发生provider端缩放。若客户端必须改变图片，固定确定性变换并将最终发送图片及摘要入计划，保持G0/D0可视化语义一致，不静默改变S1显示协议。
- 输入上限12000 tokens必须包含系统提示、公共JSON、修复错误码、两张图的计费/上下文折算。输出最多256 tokens。不得只使用当前S1“文本字节数≤12000”的检查替代完整预算。
- 冻结tokenizer/估算算法、误差和保守余量。provider不支持精确预估时，使用有依据的保守上界；无法约束则 `BLOCKED_TOKEN_ACCOUNTING`，不得假装已满足。超长在发送前拒绝，不自动删字段、降低图像质量或换模型。
- 真实预检分别记录“本地图片正确编码”“最终发送体带图”“服务接受并返回对应模型元数据”“图像输入能力验证”四类证据。仅有SDK返回200或模型自称看到了图都不足以单独证明图像链路正确。
- 图像能力验证使用预先声明、独立于装载策略的合成视觉探针，分别覆盖workspace/candidates两条图片路径；记录输入、可核对视觉事实、原始输出和判断。探针不进入正式数据或经验库，不提供装载策略答案。模型识别失败按证据诊断，不能通过不断修改探针直到通过；失败后的修订另立预检版本。
- 可用前8单的固定公共状态验证真实选择契约，但该单步预检不算完整pilot订单记录，不替代整单运行，不计入新的独立来源。所有预检请求单列账本。
- **本版建议预检总上限8次真实请求尝试**，其中每个选择契约决策仍≤2次。实际探针/契约任务表、请求数和金额必须在调用前冻结；如不足以预检，交付BLOCKED并另批新计划，不自动扩额。

### W3 全局预算、费用预留与崩溃恢复

建议新增 `o5/remote_budget.py`；远程账本使用新schema，不覆写S1的 `real_api_attempts=0/test_double=true` 记录。

**预算层级：** 预检阶段、pilot阶段、job、决策attempt。预检与pilot分别计数和限额，并有覆盖两者的总金额上限；G0真实请求数和费用必须为0。

|字段组|必须记录|
|---|---|
|身份|plan/run/job/task/request/state/attempt ID，repair序号，方法，真实/替身标识，配置/公共请求/发送体/图片摘要|
|发送状态|planned/reserved/sent/completed/failed/unknown及时间；provider请求ID；网络结果是否确定；错误类别|
|token与计价|发送前输入/图像/输出上界，价格版本/来源/获取日期，usage原件，cache/图像/其他计费项适用说明|
|金额|币种、预留额、已结算额、保守未决额、剩余预算、actual/estimated/unknown依据及精度|
|恢复|最后持久化点、原始响应位置/摘要、已提交状态摘要、只读对账事件和操作原因|

先在全局排他锁内校验请求数和金额，持久化预留，再写sent后发送；返回后先保存原始响应/usage，再解析并提交动作。预留公式和向上舍入使用确定性十进制规则：已结算费用＋其他未结算预留＋本次最坏费用不得超过金额上限。修复也重新占用一次请求额度及金额预留。

缓存优惠不能作为必要预算假设；失败、拒绝、修复和探针均计入实际或保守费用。未提供usage/账单时不能记0元；保留估算并按最坏费用占用预算。无法给出可信费用上界时禁止批量执行，报告 `COST_NOT_FROZEN`。客户端上限只能保证按已冻结计价口径的预算约束；若provider计费口径无法核实，不宣称已保证真实账单硬上限。可用账户侧额度时同步记录，但不能用它替代本地账本。

**状态语义与恢复：**

1. planned/reserved且确定未发送：校验源码/计划/账本后可发送同一attempt，不新增ID掩盖旧记录；预留不得重复扣减。
2. sent但无持久化远程结果，包括timeout、断连、进程崩溃、返回后落盘失败：记 `UNKNOWN_IN_FLIGHT`。停止整个远程批次，保留金额预留，不重发该决策，不继续消费剩余额度。
3. 已保存完整响应但尚未提交：只从原记录解析和提交，不能再次调用。重复恢复不得重复物理提交或重复结算。
4. 明确HTTP错误与确定未发送错误分开记录。普通确定服务失败终止该订单，保留分母；401/403、模型不可用、持续限流等系统性故障停止批次。首次429即暂停批次并记录，不通过自动重试消耗修复额度。
5. 已明确失败的服务请求不自动重试；格式/绑定错误才允许一次修复。同一决策网络层与格式层合计不能超过两次实际发送。
6. 缺失/篡改账本、响应、图片、映射、计划或源码时拒绝恢复，不重建空账本、不重置金额。
7. 未知结果只能用provider支持的只读查询/账单核对进行对账，不能用重复POST探测。不存在可核实查询时保持暂停；后续处置必须保留审计和原件，不伪称exactly-once。

单次响应可能不含完整usage时，只要保守预留仍有效，可按冻结规则继续；若费用已超出预估或无法继续约束，停止批次并标注差异。不得删除失败费用或用新目录重新获得同一授权额度。

### W4 计划、执行入口与只读复核

建议使用独立 `runners/o5_s2_pilot.py`；最终命名可调整，但必须提供下列职责的命令及帮助说明。以下为**目标接口草案，尚不能当作当前可运行命令**：

```text
prepare-preflight  --dataset <DATA03> --provider-config <配置> --output <新目录>
preflight         --plan <预检计划> --authorization <授权记录> --output <新目录>
prepare-pilot     --preflight <预检结果> --output <新计划目录>
run-pilot         --plan <冻结计划> --authorization <授权记录> --output <新目录>
run-pilot         --plan <同计划> --authorization <同授权> --output <同目录> --resume
verify            --experiment <运行目录>            # 零网络，只读
report            --experiment <运行目录> --output <新报告目录>  # 零网络
freeze-d0         --experiment <通过的pilot> --output <新封存目录> # 零网络
```

准备命令默认零网络；计划存在null/UNKNOWN关键参数时保持DRAFT，不可执行。远程命令校验具体计划摘要、授权阶段、账户、币种和金额，不因本规范存在而视为已授权。授权记录应可追溯到用户的实际指令，不能由程序自行生成“用户已批准”。

固定 `development_001`—`development_008`，G0/D0各一次，共16条计划记录。实际任务内容和原始来源、整单长度保存在评估侧，不发送给模型。D0 attempts上限为2×这8单全部箱数=290，仍受总规范320上限约束；即使早停也不把未用额度挪给新增订单。G0调用数0。

### W5 Pilot评估、难度诊断和D0封存

逐单报告G0/D0：完整箱数/体积分母、实装箱数/比例、VR、容器利用率、完成标志、每步候选数、主动STOP/空池/格式/绑定/物理/服务/预算停止原因、尝试数、修复数、usage、费用及端到端耗时。

工程指标按原始整数报告：

- 每个计划决策实际发送≤2；所有实际发送和物理提交100%可追溯；实际提交物理违规=0。
- 最终协议合法率≥98%。本文件固定分母为“D0中非空候选且已经开始至少一次实际远程请求的决策数”；分子为这些决策中在≤2次尝试内获得schema、request_id/state_hash、候选/STOP全部合法响应的决策数。服务失败、拒绝、截断、最终格式/绑定失败记分母不记分子。
- 空池未调用决策、发送前预算拒绝不进入上述协议分母，但必须单独列数并保留订单总分母。分母0时合法率为null，不得写100%；不能据此通过真实协议验收。
- 首次合法率、最终合法率、格式修复率分别报告；物理拒绝另报，不可用格式成功掩盖物理失败。未开始/未知请求等导致计划不完整时，即使已执行子集合法率很高，也不得判整阶段PASS。
- 8个来源只是pilot，不进行正式性能显著性结论，不将逐步决策数当独立订单样本。

难度与研究准入分开：

|观察结果|必须采取的动作|
|---|---|
|两方法均≥7/8单完成且平均VR均≥98%|`CEILING_RISK / HOLD_DIFFICULTY`，先分析任务分布，不扩大付费矩阵|
|完整完成率接近0，或空候选早停集中|报告完成数、VR、到货长度、停止位置、候选覆盖/物理检查原因；区分候选覆盖、可行性未知与模型失败，不宣称全局无解|
|无天花板风险、协议合格且难度证据可解释|可封存D0，并提交是否进入S3的建议；不要求D0高于G0|
|难度原因仍不清楚|工程可标PASS，研究准入HOLD；不得直接扩至60单训练采集|
|发现协议/数据/物理配置实质错误|当前版本INVALID，保留原件；另立版本与计划，不覆盖结果|

低完成率不自动判失败，也不自动判“可继续”：需给出诊断与剩余不确定性，不能为了获得完成率修改候选、容器、订单或选择策略。超出本阶段的难度诊断工作另立计划。
