## 2. 推荐：当前公开运行时快照＋最短roundtrip十进制

推荐为**已知运行时int/float值创建新的公开快照来源**。对有限binary64 float以冻结CPython的`repr(v)`取得最短roundtrip十进制，再按该十进制的数学值转Fraction进行新几何计算；int按原整数值。该profile拟名`geometry_runtime_shortest_decimal_v1`。不从来源文件追溯词素，不声称repr就是初始输入数字。`repr(v)`不是固定小数位格式，也不是“足够接近便取整”。

主要依据：当前公开观察、JSON记录与既有物理入口本就传递int/float；最短文本可在同环境下恢复同一binary64，便于核对公开观察和保存状态。它避免把常见显示十进制`0.0005`内部略大的binary64展开误解为“原任务本来就大于半格”。精确几何仍保留快照中可见的`0.30000000000000004`，不吞掉算术残差。输入不做0.001mm量化；只在最终提案发布时依既有规则量化一次。

这是为新运行协议作出的语义选择，**不是比精确binary64更准确的普遍结论**。它在新几何的精确谓词中采用“快照十进制值”，不采用“内存位模式的精确实数值”；与旧E2内部浮点运算也非逐中间步骤相同。新几何/旧物理之间仍可能有边界不一致，必须保留错误和拒绝，不能以本推荐保证所有状态可接入。

| 路线 | 几何取值、已知信息 | 优点 | 限制/本轮结论 |
|---|---|---|---|
| 最短roundtrip十进制 | 对每个已知float取repr十进制精确值；当前快照是新来源 | 与可观察JSON表达接近，解码恢复同一float，文本短且可核对 | 与精确binary64并非相同实数；对表达和运算顺序敏感；**推荐，待QA** |
| 精确binary64十进制 | 以`as_integer_ratio`/`Decimal.from_float`精确展开当前float，几何用相同有理数 | 忠实于位模式的实数值；不依靠最短文本推测 | 文本较长，0.0005半格方向改变，常见十进制面可能有精确微缝/微叠；仍不能恢复原词素；保留为未批准对照设计 |
| 原词素侧车＋派生字段协议 | 原来源字段保留原字节/逐叶指针；派生载荷/位姿另定语义 | 可审计原输入十进制含义，适合从新入口开始完整建链 | 当前state不携带该侧车；原词素有时合并丢失，派生量本来没有原任务词素；需贯穿到货/提交/恢复，不能只在provider回读未来task；不推荐本轮首选 |

无论选择哪一种，新profile不能冒用GP0 `exact_decimal_rational_then_binary64_original_checks_v1`的原词素来源含义。原GP2独立入口不判错、不废弃。后续若改推荐，新增profile/重新审查，不在同名profile下更换解释。

## 3. 公开来源与逐字段语义

实际链路为`ledger.read`普通JSON解析 → `packaging_runtime.runtime_task`复制静态属性 → `buffer_state.initial/receive`保存当前容器与已到货缓冲 → `episode.decision_inputs`从内存state构造observation → `candidates.current_state`公开白名单投影。`evaluation.state.apply_candidate`生成提交后的位姿、面积分载支撑边与累计载荷；`domain.restore_placed`是生成端原物理重建路径。以下将**当前保存值**与**生成端重建值**分开。

原任务数值词素、原空白/指数写法及进入float前的任意多位小数，在当前state中不可得，标记`NOT_AVAILABLE_IN_CURRENT_STATE`；不能仅凭已知任务目录/摘要宣称已恢复。当前state中的int/float值、类型、浮点位模式、数组顺序、计数和关联ID可得。派生值是已执行算术产生的观察事实，不存在待恢复的“原任务载荷词素”。

## 4. 两份字节与新profile的严格边界

### 4.1 原生运行时快照 B_native

拟议`geometry_runtime_state_snapshot_v1`，顶层封闭为`version/current_state/observation`；current_state使用现有STATE_KEYS及ITEM_KEYS白名单的独立封闭Schema，attributes各嵌套对象显式闭合；observation使用现有公开观察字段的封闭副本/显式引用。快照不保存整task。原生state只用于核对与提供相同物理输入，不代替完整checkpoint的执行状态。

序列化冻结为CPython标准库JSON：UTF-8、ensure_ascii=False、sort_keys=True、separators=(',',':')、allow_nan=False，无BOM/尾换行。list顺序保留；对象键按Unicode排序。float采用该环境最短repr规则，原生`1.0`与int `1`、`-0.0`与`0.0`保留为不同字节/位模式，不能在状态身份中用Python的`==`混同；保存原生字节，不声称这是原任务文件。未来实现要校验解码后类型及float位模式一致，冻结CPython实现/版本、radix=2/mant_dig=53及序列化版本；不支持的环境技术拒绝，不临时换编码器。

### 4.2 几何输入 B_geometry

拟议`geometry_runtime_public_input_v1`封闭顶层必填：`version/profile/adapter/native_snapshot_sha256/effective_state_digest/observation_digest/payload`。payload封闭为`container/placed_items/buffer_items`，嵌套字段严格为第3节清单。物理连续量统一为规范十进制**字符串**（不是JSON number），ID为字符串、stackable为bool、yaw/arrival_index为int；负零在几何字符串中统一为`"0"`。数字字符串须符合规范有限十进制语法，不接受NaN/Infinity、空格、无意义尾零或任意指数别名。

对原生float的转换为`Fraction(Decimal(repr(v)))`；int为精确整数；规范文本为无指数有限十进制、去无意义尾零/-0。内部一律Fraction，不依赖Decimal全局context做加减/量化。字符串canonical JSON采用4.1同一编码规则；保存的B_geometry是本次适配新产生的原始字节，不是原GP2文件的重建。

第3节所需原生数值只接受type严格为int或float；bool只用于bool字段，Decimal/Fraction/numpy标量不偷偷转float。float须有限，包括正的subnormal；不得先round、截位或将微小值改0。int进入原物理binary64边界时必须有限且精确可表示（转换后int值相等）；不能表示者技术拒绝，不静默损失整数精度。无新增经验性尺寸截断或预算。

几何输入中每个规范十进制串都应可由B_native对应叶子按profile唯一导出；验证者不仅比较hash，还验证逐叶来源和往返float位模式。原生负零与类型身份由B_native保留，几何值规范化不更改实际提交状态。

### 4.3 坐标、计算与失败

维持托盘中心x/y、底面中心pose、z向上；几何AABB由所选profile后的坐标与尺寸用精确有理算术形成，空间顺序仍`[xmin,ymin,zmin,xmax,ymax,zmax]`。不能先在float中算角点再将结果称为相同精确几何。已有保存位姿不量化、不吸附；新提案发布`round(Fraction*1000)/1000`，0.001mm HALF_EVEN一次，尺寸不量化。只有地面/当前箱顶层，不加近似接触层。

以精确profile形成的面可能与原float运算面不重合。比如输入z=0.1、h=0.2：最短profile内部箱顶是精确0.3；原float算顶得到0.30000000000000004。若另一个z已保存为0.30000000000000004，它在最短profile下也仍是该值，不被自动当成0.3。精确微缝/微叠可影响空间谓词；原物理1e-6只在原物理函数内起作用，不能扩散为新几何epsilon。

缺字段 → `RUNTIME_INPUT_MISSING_FIELD`；非法类型/非有限/非法ID/结构 → `RUNTIME_INPUT_INVALID`；不可表示/溢出/非零下溢 → `RUNTIME_NUMBER_UNREPRESENTABLE`；快照与公开状态/别名/字节绑定冲突 → `RUNTIME_SNAPSHOT_MISMATCH`。这些是拟议错误码，公共循环尚未实现持久化。正常完整空池仅保留OK_EMPTY；非法输入或精确前缀矛盾不能冒充无物理候选。

输入不修改源state；原几何范围/包含/无正体积重叠检查若发现与原物理容差接受的前缀冲突，记录`RUNTIME_EXACT_STATE_CONFLICT`技术停止，不先round输入解决。该精确前置检查须作为新协议两后端共同的状态可比较性检查，不能只在新后端失败后把旧后端成绩计为同一有效状态上的胜利。

原检查和预算一律保留：原提案evaluate_pose、发布pose复核、独立check_candidate；失去host/改变高度/表示不一致仍拒绝；发布检查与oracle差异仍为`PHYSICAL_CHECK_DISAGREEMENT`整体ERROR。真实2.0004mm差异不得修容差消除。4096/2000000/16384/2000000/32768预算、16/48、0/90与96000请求字节上限不变；本设计没有测足够性，也不授权放宽。数值转换失败/资源错误须技术停止，无部分候选或后端回退。

core的输入参数须显式区分`exact_geometry`、`native_physical`、`identity_namespace`与`source_contract`；旧词素视图不能从native_physical反推，新视图不能标为original-lexeme。GP2旧CONFIG预算/压缩规则不变，新runtime身份在独立wrapper显式绑定，不能因抽取core就复用旧审计版本虚称来源相同。重构会改变宽范围源码身份，旧冻结checkpoint按原规则拒绝；不重签历史。

**载荷边界**：保存账本是快照事实；原E2和新GP2路径都使用原`domain.restore_placed`构造生成物理状态。新入口继续复用该重建与GP2已有保存载荷/支撑一致性校验（包括其既有允许舍入的比较），记录保存值和重建值身份，不让新Fraction算术重写账本，也不增加“精确分数和必须等于1”的新规则。共同前置校验拟从原适配/校验中复用而非再造另一套分载器；若两后端实际物理视图不一致，技术拒绝该比较而不是择一覆盖状态。本轮没有执行该重建或证明其接入通过。

## 6. 两后端的公平输入与解释边界

同一新v14运行协议中，两后端先绑定完全相同的B_native、有效公开状态摘要、B_geometry及profile。共同前置检查包含当前observation一致、数值准入、精确前缀有效性及原载荷/支撑校验。E2仍使用原生物理状态和原`generator_config()`语义；新后端用同源profile exact几何提案，并向原物理函数提供同一可恢复的原生值。不能将几何规范文本的变化写回E2 state或将其全部字段强制float化，改变int/float身份。

E2原算法保留其float中间运算、旧点集和压缩；新算法采用精确有理几何及新压缩。即使共同输入profile固定，**完整后端比较也包括它们各自的中间数值算法**，不能声称仅证明EMS采样的因果收益或所有中间坐标相同。若后续另获授权比较profile，必须固定backend、同一B_native、原物理和配置，只改profile，单列数值敏感性；不与“旧E2/新候选器”的主比较合并，不从本设计推导运行额外矩阵许可。

候选机制比较的配对键至少为native_snapshot_sha256、effective_state_digest、profile、原物理/监测身份、预算/F0合同；backend及其必要配置是被比较项，不能混进公共状态键。同一状态两后端的request_id/state_hash按现有观察产生，F0问题、字段、匿名映射和排序/洗牌规则一致；seed仅display_order_seed/request_id/state_hash，不能加入backend/job/candidate_id/profile来制造后端相关展示。profile固定；若profile变化导致状态不同，不声称展示仍可直接配对。

backend、profile、来源、host、压缩理由、快照技术字段和监测诊断只在审计/本地绑定，不进入Jev请求。无F1、无经验。raw_valid_candidates与TopK后的physical_candidates分离，selectable=最终physical池；E2没有同口径raw_valid审计时明确NOT_AVAILABLE，不能伪造为新后端原始池计数。

原v1—v13默认调用不经过新profile准入，不改旧Schema。新v14的同状态准入可能比旧E2运行入口更严格，须明示新协议有效域，不拿旧历史job直接归因。共同前置失败应保留两后端`NOT_COMPARABLE_RUNTIME_INPUT`及失败原因；新后端内部生成ERROR则保留该backend的ERROR，不把它升级为共同输入失败替其免责。

## 7. 身份摘要和检查点设计

### 7.1 独立绑定

`geometry_runtime_binding_v1`拟议封闭字段全部必填：`version/native_snapshot_sha256/geometry_input_sha256/effective_state_digest/geometry_values_digest/observation_digest/profile/adapter_version/adapter_source_digest/source_manifest_digest/config_digest/backend/physical_identity/monitor_identity/data_identity/task_identity/environment_digest/serializer_version`。每个摘要为原字节SHA256或本节明示的规范JSON语义SHA256，不靠路径作为身份；自身record_digest不纳入自身计算。

- native_snapshot_sha256与geometry_input_sha256分别哈希两份**保存原字节**。保存时固定编码，不在恢复时用新的repr重发文件以取得“相等”摘要。
- effective_state_digest哈希从B_native白名单投影的原生有效输入：容器、顺序化placed、按arrival_index的pending及slot/计数/流结束状态。按同一原生canonical编码，含保存账本和类型/负零信息，不含backend/job/profile。旧observation的state_hash未覆盖保存账本，不能单独替代它。
- geometry_values_digest哈希第3节规范几何payload；profile另单独绑定，即使恰好两个profile在某状态生成相同payload，也禁止跨profile恢复。
- source_manifest_digest覆盖生产全部py/json；另记录适配器/serializer源码、配置身份。config摘要含所选profile、数值编码、预算、压缩、feature/监测开关等；独立物理清单与监测exact v3身份分开；数据/task和依赖环境保留既有身份检查。
- environment记录Python实现/版本、浮点radix/mant_dig、序列化版本、依赖清单与原监测执行环境，封闭Schema的键名须在实施时枚举；不得凭“数值看似一样”允许环境漂移。本轮只观察Python，不导入生产依赖。

profile属于恢复身份而非展示seed；路径、墙钟耗时和日志格式不混入语义动作键，环境/源码身份不因其不影响某个样例就豁免。

### 7.2 保存和恢复

这是未来checkpoint_v14的设计要求，不是本轮生产验证：新决策开始时先持久化不可变B_native、B_geometry和binding，再允许生成。checkpoint保存完整原state/cursor/decision/phase、这些字节的内容寻址引用及摘要、bundle与geometry_audit引用、context/映射、选择/发送账目、已存monitor和提交事件。外置blob必须先原子写入并校验，再发布checkpoint引用；若不能确保持久化，就停止，不继续发送或提交。

恢复按顺序核对：原checkpoint封闭版本及record摘要 → blob原字节摘要 → 所有profile/配置/源码/数据/物理/监测/环境身份 → B_native/B_geometry逐叶关系 → 阶段对应的state和观察绑定。缺blob、重复JSON key、非法编码、未知版本/字段、profile不支持或状态变化一律拒绝，不从当前state/task重建缺失blob，不重签旧摘要。仅有语义相等而原字节不同（空白、类型或负零变化也可能被`==`忽略）不足以接受替换。

| 阶段 | 输入/state绑定与复用 | 禁止的恢复动作 |
|---|---|---|
| READY，尚无决策blob | 核对当前state/身份后为新决策采集；若已有blob但无pool则只复用已存字节 | 用不同profile补同一决策，或覆盖已保存blob |
| 已有pool/context但未选择 | 复用原blob、pool、context/映射与账目 | 生成新pool替换；UNKNOWN_SEND隐式重试 |
| SELECTED | blob须与pending_event.before及cp.state一致；复用已存选择 | 重发选择、改选其他候选 |
| MONITORED | 同before绑定，复用已存monitor原结果/凭证 | 重新求解、覆盖监测或改精确动作 |
| COMMITTED | blob绑定pending_event.before；cp.state绑定pending_event.after和提交凭证 | 错把blob要求等于提交后state；再次放置/移缓冲/增加计数 |
| TERMINATED | 历史决策blob绑定各自before；终态沿原账目核对 | 将终止当空白新决策恢复；改写失败分类 |

完整保存state仍由公共checkpoint拥有。B_native只取当前公开子集，不能凭它初始化任意历史订单或迁移v13/v12checkpoint。审计已提交状态可在私有副本上按原恢复协议核对，但不得把验证重建当作再次真实提交；本轮不执行任何恢复或重放。

后续新协议保持“选择保存 → 只监测已选精确动作 → 监测保存 → 提交/分类停止”，指定exact_freeze/exact_adapter v3。新执行计划显式启用监测，只有STABLE允许原commit一次；若设计保留关闭模式，DISABLED单独记录并在新协议停止为`GEOMETRY_MONITOR_DISABLED`，不借旧历史DISABLED可提交行为绕过。旧协议行为不改。此处仅澄清待实现分支，不运行内核。

## 8. 限定数值例证与本轮验证

脚本仅导入标准库Decimal/Fraction/json/math/struct等，未导入工程模块。实际Python为CPython 3.13.5。数学量化通过Fraction的ties-to-even计算，不受Decimal默认精度影响。

| 例证 | 本机结果 | 设计含义 |
|---|---|---|
| `0.1`和`0.10000000000000001`原词素 | 两者Decimal不同，但float相同 | 原来源不可逆；新快照必须另立来源声明 |
| runtime `0.0005` | 最短profile为精确0.0005，HALF_EVEN到0；精确binary64略大，量化到0.001 | profile能改变发布动作，不可同名混用；只验证算术，不验证可行性 |
| 已存`0.1+0.2`与字面`0.3` | 保存float分别为0.30000000000000004和0.3；两个profile均不认为两保存层精确相等 | 不自动吸附或删残差；原物理容差的算术比较不是实际检查通过 |
| profile内部`0.1+0.2` | 最短值精确相加等于0.3；binary64有理数精确相加不等于binary64的0.3，也不同于native舍入后的和 | “转换保存的和”与“先转换操作数再算和”必须区分；几何按输入叶子精确运算，已存载荷直接保留 |
| 派生账本类比`0.2 + 0.1*(1/3)` | native保存0.23333333333333334；用最短操作数重算为0.23333333333333333 | 不以新的精确运算重写已执行账本 |
| JSON往返与恢复字节 | 数值fixture往返字节/float位模式与类型相同；一ULP变化hash不同；同值不同空白原字节hash不同；profile变更binding hash不同 | 原blob应复用，不靠JSON对象`==`或重序列化重签；未验证生产checkpoint |

JSON fixture是六个数值叶子，不是新Schema实例、订单或checkpoint。负零仅在几何规范文本归0，原生身份保留。NaN编码拒绝亦由标准库例子验证；不据此声称所有拟议结构/失败码已通过生产测试。
