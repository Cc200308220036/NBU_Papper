## 2. 工程主线如何演变

历史O4主要研究“语言业务要求→规则AST→程序筛选/规划”。模型主要参与规则编译，实际选址由本地算法执行。旧实验中模型与Parser结果一致，不能作为模型直接选动作的能力证据。

Jev新链将模型接到候选生成之后，直接选择动作。它不是替换旧RemoteCompiler的模型名称，也不生成AST或连续坐标。内部Parser和AST仍服务于公开规则表达、本地基线和评价基础设施。

阶段状态如下：

| 阶段 | 已实现内容 | 证据限制 |
|---|---|---|
| J0 | 候选、公共上下文、编号映射、请求导出及Schema | 本地有离线产物，不证明模型质量 |
| J1 | 选择器、整单闭环、账目、恢复及离线替身 | 替身不是Jev推理 |
| J2 | 原生Choice真实服务路径 | 报告记录四箱构造订单4/4完成、违规0，仅为冒烟 |
| J3 | 三箱真实来源几何订单、合成业务任务、三方法对照 | 文档报告正式运行完成；本地缺少正式原始产物 |
| J4/经验 | 仅有接口预留和研究方向 | 非空记忆被明确拒绝，不能称为已接入 |

## 3. 当前J3实际决策过程

`fill_then_plan`到货并填充三箱缓冲后，`CandidateProvider`调用原E2物理候选器，为每箱生成最多16个动作，联合最多48个。所有保留的物理候选进入选择池，不按业务规则删除。

`ContextBuilder`提供当前已放箱、可选箱、商品属性、容器、区域、业务要求、候选位姿、支撑、载荷变化及几何特征。对象改为Bxxx，动作改为Cxx；本地保留原始身份与摘要。模型不接收未来到货、参考答案或每候选的业务违规评分。候选仍含geometry_score及heavy_low/center特征，因此它是在程序候选与特征辅助下选择。

多候选时Jev返回一个Cxx。`selector.py`校验服务模型、选项、概率与usage；`execution.py::commit_physical`恢复该候选并复查物理条件，随后仿真提交。提交后独立业务评价；业务违规不阻止下一步。单候选由环境自动执行，空物理池由环境停止。

物理不可堆叠、物理承载、碰撞、边界和支撑仍为执行条件。业务禁压、业务限载、禁接触、区域及相对位置属于评价目标。不能把“业务违规可执行”解释成取消物理承载检查。

关键接入点：

| 模块 | 后续开发用途 |
|---|---|
| `candidates.py` | 同状态物理池及候选覆盖诊断 |
| `context.py` | 输入特征、提示与经验上下文 |
| `selector.py` | Choice契约、本地基线、新选择器 |
| `transport.py`、`ledger.py` | 网络诊断、发送账目及恢复 |
| `execution.py`、`episode.py` | 保持动作绑定、提交与评价顺序 |
| `dataset.py` | 来源分组、受控业务属性、数据划分 |
| `batch.py`、`evaluation.py` | 计划冻结、批量运行与分层指标 |

## 5. 后续开发顺序建议

### 第一步：对齐基线和研究任务

先恢复正式J3计划、metrics、账目、源码快照和必要轨迹，确认后续使用的版本；恢复文件不要求重新付费或全轨迹回放。若暂时无法恢复，则把J3数值保留为文档记录，新开发使用新计划，不宣称复现J3。

目前本地唯一O5详细规范日期为2026-10-27，要求单箱、图文、无业务指令；J3是三箱、文本Choice、显式公开业务要求。两者是不同实验协议，不能直接拼接。缺失的2026-10-28隐藏业务反馈方案应恢复后再核对；在此之前不能推定其反馈时机和可见字段。

若研究公开业务要求下的策略经验，可直接以J3为基础扩展J4。若研究隐藏业务反馈学习，则先明确训练/测试阶段能看到什么、何时收到业务反馈、哪些属性隐藏，以及如何限制当前参考规则进入选择器或总结器；现有J3输入不能原样充当隐藏规则任务。

### 第二步：先定位接口提前停止

在新开发协议中分别记录连接、超时、HTTP、响应读取和解析阶段的脱敏错误码及耗时，避免所有网络错误只留下UNKNOWN。对choice_not_maximum先核对服务输出契约与量化行为，不擅自把返回choice替换为argmax，不为了通过而直接扩大容差。

这些诊断只改变可观测性或形成新契约版本，保留J3原始失败。任何重试、接管或兼容策略均作为新版本、新方法单独测量，未知发送仍不能无账目重发。

### 第三步：分开诊断候选与选择

仅使用开发来源建立相同状态的决策题，比较Jev、几何和公开业务启发式。检查差异来自选箱还是选位、当前新增违规还是后续空间受阻、候选显示顺序还是几何特征依赖。

同时记录采样池数量、TopK保留数量、业务无违规动作是否存在。当前TopK有方向/间距及区域代表保留机制，并非简单按分数取前16；模型只能在保留下来的候选中选择。空TopK不代表连续空间全局无解。可在少量开发状态中对扩大采样或额外分支进行独立诊断，标明额外计算预算，不能混入正式Jev成绩。

为小规模业务开发题提供经过验证的完成见证，并保留已知矛盾题，有助于检验评价和策略；不据此删改历史测试任务。

### 第四步：接通最小经验闭环

当前`ContextBuilder`和`validate_context`均固定空记忆摘要，配置限制`memory_mode=none`。接经验须同步修改配置、Schema、快照、请求绑定、验证、计划冻结与恢复路径，不能只在提示里插入几段文字。

先实现版本化只读经验快照和确定性检索，再接训练订单终止后的经验生成、候选卡验证与激活；最后才接ReMe实际调用。经验只影响候选选择，不能静默改物理池、规则或提交动作。服务失败不能被总结为摆放策略。

建议比较无经验、原始历史、经验卡三个Jev方法，并保留公开业务启发式；基础模型、任务、输入、候选、传输与预算保持一致。原始历史和经验卡使用相同训练来源及附加上下文预算，以区分“多给上下文”与“提炼经验”的作用。

### 第五步：冻结新评价

J3测试结果已被查看，若据此开发后再测试，应称已见来源后续实验。经验从训练来源沉淀，验证来源用于定版，新的未见来源用于最终测试；来源分组不能被B1/B2、语言或buffer变体拆开。

分别报告系统失败、完整装入、件数/体积覆盖、业务事件与规则匹配覆盖、时延及全部经验维护成本。不同目标有权衡，评价顺序或约束应在新实验前明确，不能运行后挑有利指标。
