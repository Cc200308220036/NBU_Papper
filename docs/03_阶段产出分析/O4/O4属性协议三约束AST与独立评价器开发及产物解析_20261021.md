## 2. 代码架构与职责

实现位于`semantic_pallet_planner/src/semantic_pallet_planner/o4/`，封闭schema位于同包`schemas/o4_*.schema.json`；本轮没有给旧V2政策schema增加字段。

| 模块 | 已实现行为 |
|---|---|
| common.py | 无业务判定的规范JSON、SHA256、schema加载、错误码及字段访问 |
| observation.py | 准确属性派生、原物理限载一致性检查、公共白名单观测、摘要与引用校验 |
| fixtures.py | 独立声明六份业务任务、36个金标准、六种包装画像和文本生成；不调用待测解释器求期望 |
| dataset.py | 从只读数据集派生属性和24锚点、144固定题及72整单定义；保存来源与配对依赖 |
| compiler.py | 解析公开组合中文语法和规范完整作业单，绑定响应；不读取参考答案表 |
| normalize.py | 选择器/AST校验、重排规范化、按对象生效的限载与显式覆盖 |
| executor.py | 运行侧支撑和累计载荷恢复、直接接触、before/after、业务允许候选；不提交在线动作 |
| evaluator.py | 独立对象匹配、覆盖、载荷递归传播、接触与参考允许集合；不导入运行执行器/编译器/规范化模块 |
| invalid.py | 24个可序列化非法输入配方；NaN反例在运行时注入，不向交付JSON写入非标准数值 |
| client.py | 离线响应替身、原始响应、绑定/JSON校验、最多一次格式修复及服务错误；拒绝非fake客户端 |
| runners/o4.py | 数据构建、固定题评价、验收、校验、无网络只读回放和篡改检测 |

冻结配置为[configs/o4_ab_offline.yaml](../../../semantic_pallet_planner/configs/o4_ab_offline.yaml)。本版本只允许覆盖种子；其他配额与能力边界更改时拒绝，避免把不同范围的数据标为同一交付。

## 3. 属性与业务怎样落地

### 3.1 观测事实不等于业务答案

cargo_category、packaging.reinforced、labels.no_top_load及labels.max_top_load_kg为准确公开的仿真事实。物理承载精确映射V1，质量、尺寸、stackable等保留原值。

类别不自动产生禁令，加固不自动增加承载。完整作业单明确启用哪些规则；未启用的标签不由程序暗中执行。原product_category只有electronics/general，新增细分类通过O4侧表派生，没有改写原数据。

公共请求只含当前与已到货事实、完整文本、坐标单位及绑定摘要；没有来源订单、split、参考AST、候选业务分数或未来对象。完整参考和源数据关联仅在private/。

### 3.2 完整作业单的编译过程

输入规范：

> 本订单普通箱按各自标签的累计顶部限载执行；带禁压标记的箱体禁止顶部加载。已加固且无禁压标记的玻璃制品外箱，改按订单指定的2 kg业务限载执行，替代其标签业务限载。食品外箱与清洁用品外箱允许同托盘，但不得直接面接触。所有箱体仍须满足独立物理承载限制。

编译得到四条规则：

1. r1：全部对象按各自标签限载。
2. r2：禁压标记=true的对象限值0，并在这些对象上覆盖r1。
3. r3：玻璃制品＋加固=true＋禁压=false的对象限值2 kg，仅覆盖r1。
4. r4：食品与清洁用品之间禁止直接面接触。

每步在已到货对象中展开，不预列未来ID。不将物理承载写成可被业务例外覆盖的规则。词法支持范围和错误码见[受控语法说明](../../01_技术原理与数据规范/O4/受控中文编译语法与错误码_20261021.md)。

### 3.3 正确案例：加固小家电不套用玻璃制品例外

读取`metrics/gold.json`中`case_id=overrides_5`：

- base是电子产品、已加固、无禁压，标签限载8 kg。
- top为3 kg，放在base上；top自身标签限载5 kg，目前顶部载荷为0。
- r1在base上生效；r3的货物类别条件不满足，不能把base改为2 kg。
- 两个解释器均重算base累计顶部载荷3 kg、业务限值8 kg，允许集合为`["TOP"]`。

对应`overrides_3`则是加固玻璃制品，例外确实生效：3 kg超过2 kg，允许集合为空。只检查“已加固”而忽略类别会把这两例混淆，金标准会直接判错。

### 3.4 合法但错误AST：缺少禁压规则

读取`metrics/injections.json`中`name=missing_rule`。其公共输入来自`no_top_load_1`：base应禁压，TOP给它增加1 kg载荷。

测试替身故意返回合法空规则AST。响应结构及绑定通过，系统不索取参考答案、不补回禁压规则；方法因此放行TOP，而独立参考允许集合为空。原始错误AST、方法结果、参考结果及语义反例全部保留。

这是“格式正确但业务错误”的可观察案例，不是API调用失败，也不是用屏障纠正后的模型成功。错对象和错阈值另有两项注入。

### 3.5 无参考可行候选：不等于整个订单无解

同一`no_top_load_1`金标准只给定TOP这一个候选。正确执行规则后，base载荷1 kg超过0 kg，运行侧和参考侧均返回空集合。

这里能得出的结论仅是“给定状态/候选集合无业务可行项”。本轮不运行在线Planner，不证明全连续空间或完整订单无解；不会因此删除样本，也不计作无违规整单完成。
