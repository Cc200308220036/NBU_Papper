## 1. 开发位置与模块连接

为保留A/B平铺源码清单与C冻结文件，本轮使用规范所列六模块的等价子包组织：`semantic_pallet_planner/src/semantic_pallet_planner/o4/buffer/`。原A/B、C与旧生成器文件不修改。

| 模块 | 职责 |
|---|---|
| `buffer_state.py` | 唯一真实待码状态更新入口；接收、槽位、EOS、守恒、独立物理提交；搜索只对克隆值调用 |
| `buffer_protocol.py` | 封闭公共观测、缓冲状态、业务响应及WAIT/PLACE动作；全状态绑定与语法解析适配 |
| `buffer_candidates.py` | 每个待码箱独立调用冻结单箱生成器；每箱Top-K、唯一联合标签、业务/物理与软预算评价 |
| `buffer_baselines.py` | 严格FIFO、业务可行候选数/质量/到货顺序的启发式基线 |
| `buffer_search.py` | 深度3、束宽8、至多256次后继评价的确定性束搜索；叶评分及保守预算截断 |
| `buffer_evaluation.py` | 真实到货环境与公共规划边界、逐事件闭环、原始提议/提交、下游独立参考评价及指标 |
| `cases.py`、`validation.py` | 预声明构造、独立小规模枚举、状态机金标准及错误注入/隔离诊断 |
| `runners/o4_buffer.py` | 完整矩阵、冒烟、容量1/2/3试跑、恢复、只读回放及保护检查 |

新增四份schema：`o4_buffer_observation`、`o4_buffer_state`、`o4_buffer_response`、`o4_buffer_action`。单箱A/B观测的`available_objects`上限为1，不能直接承载三箱输入，因此缓冲观测采用独立版本，上限为3；原观测schema不扩写。业务AST继续使用同一个`o4_policy_v1`，含义与原三约束一致。

## 2. 实际作业链与信息隔离

环境持有完整订单；规划状态只持有已到货对象的原始事实、属性、暂存槽位和已码托盘。业务编译接收这些公共事实和业务文本，调用已发布的中文语法解析器；不按请求ID检索答案。

运行顺序为：请求下一次到货 → 接收一个箱或EOS → 补满待码区或收到EOS → 在真实公共状态上编译一次业务AST → 每箱独立生成候选 → 应用三类业务约束及相同软预算 → 规划对象、顺序和位置 → 提交首动作 → 补货并重新规划。

搜索树中不再编译、不调用网络，也不读取私有订单、参考策略或下一箱信息。私有Oracle只在Oracle对照入口提供AST；普通强规则方法的实际选择完成后，独立参考评价器才检查结果。合法但错误的AST会保留其错误提议和实际业务违规，不用参考答案回填。

`buffer_state_hash`绑定公共托盘、待码事实与槽位、容量、事件计数、EOS及业务文本摘要。响应与动作绑定该哈希及事件序号；PLACE另绑定候选集合、箱ID与候选指纹。提交前核对公开位姿与原始物理候选，禁止“业务检查一个位姿、实际提交另一个位姿”。

默认EOS方式为最后一箱之后的合法空读；另有最后到货同时返回EOS的边界测试。EOS不是公开订单总数推导值。暂存意味着三个独立可取槽位中的真实未码箱，不是只记录属性再丢弃对象。

## 3. 搜索范围与评分解释

每箱最多16个候选；其他待码箱不作为已码支撑。联合动作标签同时含稳定到货序号、本箱局部候选标签及对象/位姿指纹。候选存储顺序不会改变选箱选位。

每次规划的预算包含所有已检查候选，包括业务或物理拒绝项，以及叶状态余箱可行性检查。对下一组候选先保留每箱16次的最坏情况预算；余量不足时整组不评估并明确截断，因而可能在256之前保守结束。候选生成耗时另外记录，256不是总计算量或真实耗时上限。

叶评分依次为：合法模拟件数、已放体积占初始待码总体积比例、剩余箱业务可行数、暴露可堆叠顶面比例、较低垛高，最后按到货序号与候选指纹序列破同分。连续层使用固定最大值锚定的`1e-12`同分；余箱可行性未完整计算时，该比较层对全部叶统一跳过。束搜索保留8个节点，不能保证保留所有潜在可行路径或全局最优布局。

实际只提交最佳路径的第一步。新到货或真实状态改变后丢弃模拟路径，重新规划。

## 4. 数据与预声明功能案例

正式任务沿用冻结的12个train开发来源×6业务配置，共72个完整订单。四种Oracle规划器为`single_greedy`、`buffer_fifo`、`buffer_heuristic`、`buffer_search`；另用强规则编译器复算72条搜索轨迹，总计360条逻辑记录，全部新运行。独立重复与中断恢复分别单独记账，不增加独立来源数。

24个状态机/规划金标准涵盖容量1/2/3、独立槽位、满缓冲、EOS、尾单1/2箱、非法WAIT/PLACE、失败不删箱及搜索配置边界。

12个跨业务构造按四类各3例组织；期望先由几何与业务算术声明，再用不调用搜索器或执行器业务判定的独立参考小规模枚举复核：

| 类型 | 决策机会的独立含义 |
|---|---|
| 承载/禁压与支撑 | 首到禁压箱不能承受后续堆叠；后到箱可形成支撑后再放首箱 |
| 不同尺寸填充 | 先放小箱会使大箱支撑不足；先放大箱后放两个小箱可完成 |
| 禁止直接面接触 | 食品与清洁用品之间需要普通箱隔开；重排后形成合法三层 |
| 条件与例外 | 加固玻璃箱按显式覆盖限值执行；标签、条件和例外共同改变可选顺序 |

四个指定机会例均要求合法改序，至少两个要求增加件数或恢复完成；另外保留不少于四个无进度收益或仍无解案例。独立枚举范围是小案例的冻结Top-K树，不是连续空间全局最优证明。

开发中曾试用条件例外限值2kg：默认束宽可能保留较早到货、但后续不通的等分前缀。该现象说明有限束宽的限制。本轮功能案例将条件例外明确冻结为0.5kg以形成可核查的决策机会，预算保持默认；没有使用模型表现选例，也没有将这个构造收益外推为自然订单平均收益。

完整作业示例`O4F_load_support_0`：100×100mm托盘上，三个100mm立方箱依次到货a、b、c，每箱1kg；a带禁压标记，b/c标签累计限载均为5kg。单箱先放a后，后续顶部加载违反禁压，只完成1箱。三箱缓冲选择b→c→a，依次置于z=0/100/200mm，独立参考最终累计载荷为b=2、c=1、a=0kg，有效限值分别为5、5、0kg；三箱全部合法完成。每步仍重新构建支撑与业务规则，未把等待当放置。

错误AST示例见`cases/diagnostics.json`中的`wrong_valid_ast_visible`：强规则响应被注入合法空规则，运行端依自己的空AST提交，事后参考发现禁压违规；原错误动作与载荷保留，没有被Oracle修正。参考无可行候选示例`O4F_load_support_2`：三个箱均禁压，最终保留两个待码箱并记录业务无可行动作，独立小规模枚举也仅能放1箱，不伪造整单成功。

启发式本轮优于有界搜索，不能把“多步搜索”直接视为更好的默认方法。搜索截断率为82.47%，深度/束宽/预算及叶评分代理都可能影响结果；目前没有消融证据证明某一项是唯一原因。本轮保留冻结配置及全部退化订单，后续调整评分或预算需使用新版本，再做同来源配对比较。
