## GP3-INPUT-01：冻结词素合同与公共内存状态不兼容

这是**当前输入入口在不修订合同条件下**的冲突，不是宣称无法设计新的运行时数值协议，也不是GP2独立生成器缺陷。

冻结依据：GP0 `protocol_draft.md`“坐标、数值、动作与排序”要求从原JSON数字词素解析十进制，不从float反推丢失词素；GP2 `generator.py::generate`明确写明“must project original saved JSON lexemes, never reserialize a float mapping”。`input_adapter.adapt`要求original public JSON bytes，内部Decimal解析。`contracts.number`拒绝float。字节解析本身不能认证这些字节是否来自原文件，调用端仍须履行来源合同。

实际链路：`ledger.read`普通`json.loads`；`runtime_task`复制已解析字段；`buffer_state.initial/receive`复制容器和当前到货；`episode.decision_inputs`由内存state生成observation并调用provider；`candidates.current_state`清理公开字段，没有携带原数字词素。`evaluation.state.apply_candidate`以运行时数值计算支撑分数和累积载荷，保存到状态；`Snapshot`和checkpoint也没有逐字段原词素来源。

不能用重新读取完整未来task或私有见证来补齐；即使另建原任务字段来源侧车，提交产生的派生载荷/分数也需独立数值语义。当前恢复接口只有task/config/checkpoint，原始词素侧车尚未冻结或绑定。

本机最小反例：原字节`{"height":0.1}`与`{"height":0.10000000000000001}`通过普通JSON解析后得到相同float，Decimal解析则不同。对相同内存值重序列化只能产生同一份字节，无法同时恢复两种来源。`Decimal.from_float`可以精确保留当前binary64值，但其精确十进制同样不等于任一来源十进制。此反例仅证明来源信息不可逆，不宣称已在真实订单中测得候选差异。

因此当前不能把`json.dumps(current_state)`直接喂给原`generate`并称其满足冻结合同，也不能只重命名适配器而继续调用该禁止float重序列化的公开入口。按本轮用户明确的“如冻结合同与实际循环无法兼容，单列方案问题并停在相关接入点”停止；未删除原保护、未放宽旧Schema、未修改GP2数值定义。
