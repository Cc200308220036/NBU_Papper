## 3. GP5-P2-DRIVER-DISPATCH-01 阻断点、最小接口设计与冻结身份影响

### 3.1 源码与纯探针定位的阻断点

1. **耐久 blobs 与 `checkpoint.json`（已满足，无阻断）**：
   - [episode.py:517-550](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/episode.py#L517-L550) 在每次调用 `on_checkpoint(cp)` 和 `hook(...)` 之前，已先执行 `persist()`，其中 `geometry_store.save_input`、`save_event`（含 v17 `publication.blobs`）与 `save_checkpoint` 均已完成原子写入与 `fsync`。
   - 恢复时的 [geometry_execution.py:189-295](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/geometry_execution.py#L189-L295)`::validate_saved_checkpoint` 只校验 `checkpoint.json`、`config.json`、`task_identity.json` 和 `blobs/`，不读取 `accounting.json` 或 `run.json`。
2. **共享计数账本 `shared_call_ledger.json`（已满足，无阻断）**：
   - [geometry_order_meter.py:50-54](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/geometry_order_meter.py#L50-L54) 仅在 `exact_adapter.assess_candidate` 或 `balance_network.linprog` 执行期间将当前行标为 `STARTED`，调用返回后立即落盘 `DONE`。
   - `SELECTED` 回调发生在 `monitor_selected_action` 之前；`MONITORED` 与 `COMMITTED` 回调发生在 `monitor_selected_action` 返回之后。因此三个回调时刻 `shared_call_ledger.json` 中所有记录均为 `DONE`，无 `STARTED` 残留。
3. **单任务调用账本 `jobs/<job_id>/accounting.json`（核心阻断点）**：
   - [geometry_order_execution.py:154-160](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/geometry_order_execution.py#L154-L160) 在进入 `run_episode` 前开启 `with invocation(store.root/'accounting.json', config, job_id, resume):`。
   - [geometry_order_accounting.py:45-53](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/geometry_order_accounting.py#L45-L53) 在进入上下文时写入 `invocations[-1].status = 'STARTED'`，`result_checkpoint_digest = None`；只有当整个 `run_episode` 正常返回退出上下文时才更新为 `'RETURNED'`，或抛异常退出时更新为 `'ERROR'`。
   - 因此，在**同一次正常完成的主运行**内部，无论在 `on_checkpoint` 还是 `hook` 中复制 `jobs/<job_id>/` 目录，快照里的 `accounting.json` 末尾状态必然是 `'STARTED'`。
   - 当后续恢复调用 `run_order_job(..., resume=cp)` 时，[geometry_order_accounting.py:41](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/geometry_order_accounting.py#L41) 执行：
     ```python
     require(not doc['invocations'] or doc['invocations'][-1]['status'] != 'STARTED', 'geometry_accounting_unknown_dispatch')
     ```
     直接抛出 `JevSelectError('geometry_accounting_unknown_dispatch')` 拒绝恢复（探针在三个相位均实测复现）。
   - 同时，[geometry_kernel_completion.py:66-67](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/geometry_kernel_completion.py#L66-L67) 要求恢复后的 `accounting.json` 满足 `all(account['cumulative'][k] == sum(i['delta'][k] for i in inv) for k in delta)` 且最后一次调用 `status == 'RETURNED'`，同时禁止外部驱动手工篡改 `accounting.json` 把 `STARTED` 改为 `RETURNED/ERROR`。

### 3.2 最小接口设计

若要在**严格 4 次主运行 + 6 次恢复（共 10 次 `run_order_job` 调用）**且**主运行不抛异常、不污染主账本、外部驱动不手工改写账目**的前提下生成合规可恢复快照，最小生产改动如下：

1. **`geometry_order_accounting.py` 新增快照封存辅助函数（或上下文方法）`checkpoint_reached(config, checkpoint)` / `export_phase_snapshot(dest_accounting_path, config, checkpoint)`**：
   - 在 `episode.py::_run_episode_v2` 的 `persist()`（第 280 行，`geometry_store.save_checkpoint(cp)` 之后、`on_checkpoint(cp)` 之前）调用 `geometry_order_accounting.checkpoint_reached(config, cp)`，实时将当前活动 `invocation` 的 `result_checkpoint_digest` 更新为 `digest(cp)`（保持主运行中的 `status` 仍为 `'STARTED'`，以便进程意外崩溃时仍能识别未完成派发）。
   - 提供公开只读导出接口 `geometry_order_accounting.snapshot_for_recovery(config, checkpoint, target_path)`（或允许 `invocation` 识别显式登记的相位快照状态 `'CHECKPOINT_SNAPSHOT'` / 在导出副本中由 `geometry_order_accounting` 自身将已持久化 checkpoint 对应的副本标记为 `'RETURNED'` 并校验 `result_checkpoint_digest == digest(checkpoint)`）：
     - **方案 A（零 Schema 变更，仅改 2 个 Python 文件）**：在 `geometry_order_accounting.py` 新增 `save_phase_snapshot(store_root, target_root, config, checkpoint)`，由生产账本模块在確認 `checkpoint` 与磁盘 `checkpoint.json` 一致且当前 `_ACTIVE` 账目匹配 `config` 后，将完整 job 目录复制到 `target_root`，并在副本的 `accounting.json` 中把当前 invocation 封存为 `status='RETURNED'`、`result_checkpoint_digest=digest(checkpoint)`（主运行内存与原目录中的 `status` 继续保持 `'STARTED'` 直至主运行结束）。这样副本完全符合现有 `geometry_order_accounting_v2.schema.json` 与 `geometry_kernel_completion.py:66-67` 的累积和校验。
     - **方案 B（显式新状态枚举，需改 Schema）**：在 `geometry_order_accounting_v2.schema.json` 的 `invocations[].status` 枚举中增加 `'CHECKPOINTED'`，并在 `geometry_order_accounting.py:41` 允许从 `status == 'CHECKPOINTED'` 且 `result_checkpoint_digest == digest(resume)` 的快照恢复。

### 3.3 所需版本与冻结身份影响

- **版本影响**：
  - 采用**方案 A** 时，`geometry_order_accounting_v2`、`jev_checkpoint_v17`、`geometry_real_kernel_receipt_v3`、`geometry_kernel_required_coverage_v2` 的 JSON Schema 与运行版本号 `jev_packaging_geometry_order_v17` **均无需升级**。
  - 采用**方案 B** 时，需更新 `geometry_order_accounting_v2.schema.json`（或升级为 `v3`）。
- **冻结身份影响（关键）**：
  - [experiment.py::source_manifest](../../../semantic_pallet_planner/src/semantic_pallet_planner/jev_select/experiment.py) 会计算 `semantic_pallet_planner/src/semantic_pallet_planner/` 下全部 591 个 `.py` / `.json` 生产文件的 SHA-256。
  - 无论采用方案 A 还是方案 B，只要修改 `geometry_order_accounting.py`（及 `episode.py`），必然改变全局 `source_identity`（当前冻结为 `3b58b72f9f31913afb0e2180911dadad0c02c10f58171f8eeb632f3988b4b956`），进而改变 `acceptance_plan_FROZEN.json` 的 `plan_digest`（当前为 `2e97da50ad87c91b50b0259129f1dfc0b584e11c653d23a9a25830f3499d6433`）及所有 `strategy_identity` / `config_digest`。
  - 因此，若授权实施上述最小生产接口修改，必须在修改完成后**在原 Linux 机重新生成一套新的冻结运行包（新 `source_manifest.json`、`acceptance_plan_FROZEN.json`、`startup_review_request.json` 和零计数 `shared_call_ledger.json`）**，再由独立 QA 针对新 `plan_digest` 签发独立审查与启动记录；旧冻结包按历史归档只读保留，禁止重签旧摘要。
