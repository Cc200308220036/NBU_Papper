## 2. 早期场景如何生成

入口为 `semantic_pallet_dataset_v1/scripts/build_dataset.py`，实际流程如下：

1. 读取 BED-BPP，按箱体的 `sequence` 排序；保留毫米尺寸和千克质量。
2. 用 `normalize_source_item()` 标准化箱体。`source_attributes()` 按种子 `20260911`、原始商品 `id` 和字段名确定性生成材料、易碎、可堆叠等属性。
3. 按固定种子打乱原订单键，依次生成 train、validation、test-ID、Geometry-OOD、Semantic-OOD。
4. `choose_order_window()` 先按容器和分区条件过滤箱体，再从过滤后的序列选取连续窗口。因此，窗口不保证是未经筛除的原始序列连续片段，也不等同于完整原订单。
5. 默认每场景8—20箱、总体积占容器体积35%—80%，至少3种旋转归一化尺寸、3种高度，并满足相应 OOD 条件。
6. 生成器调用本地 `rollout()` 构造布局；构造失败的场景不会进入当时数据集。随后写出场景、决策样本、候选、参考布局、标注和划分。

默认容器为1200×1000 mm、最大高度850 mm、最大载荷1000 kg。基础场景100个：train 50、validation 10、test-ID 20、两种 OOD 各10；另有语言和缓冲配对场景。

早期承载属性的代码公式为：

```text
volume_l = length_mm × width_mm × height_mm / 1,000,000
capacity = min(volume_l × sampled_thickness × material_multiplier, 500)
```

它是合成规则，不是实测包装抗压公式。早期保留的类别/业务语义能力也不代表当前 JN 主线重新启用了这些约束。

早期生成器默认写入固定数据集目录，已有数据时需要 `--force` 才会重新生成；这会替换既有派生内容。当前冻结材料应保留，本轮没有执行它。

## 3. 当前包装订单如何合成

### 3.1 从已冻结来源快照读取

`build_packaging_dataset()` 读取 `DATA_JEV_J4_V2_20261101_03` 的既有来源快照，并核验配置中的来源文件摘要、来源审计摘要及预先冻结的包装配置。`source_bundle()` 使用已有 `DatasetOrderAdapter`，取 B1 原始任务作为包装变体的共同输入。

被冻结的4个来源及现有每变体箱数为：

| 原始来源键 | 每个包装变体箱数 |
|---|---:|
| `00100027` | 19 |
| `00100090` | 14 |
| `00100150` | 18 |
| `00100153` | 15 |
| 合计 | 66 |

这4个来源已经用于训练/开发，不能重新拆分或改名后当作独立未见测试。包装生成器继承快照的原始到货顺序，不在生成包装变体时按算法成绩挑箱或换序。

### 3.2 保留物理来源，指定包装档位

`materialize()` 保留来源箱体尺寸、质量和到货关系，设置包装字段：

- `sku_id`：既有适配/校准链给出的物理商品身份。
- `packaging_profile_id`：包装档位及容量因子身份。
- `stackable`：是否允许直接承托后续箱体。
- `max_top_load_kg`：顶部承载上限，不包含自身质量。
- `top_load_limit_kg_synthetic`：与上限相等的兼容字段。
- `effective_top_permission_kg`：可堆叠时等于上限，否则为0。
- `original_physical`、`physical_provenance`、`capacity_provenance`：保留来源和属性性质。

受控包装使用冻结训练标定：唯一物理 SKU 质量的75%分位数为8.586 kg，向上取整得到9 kg标尺。该标尺及下表都是实验设定，不随正式 test 分布重新拟合。

| 包装档位 | 哈希分配概率 | 可堆叠 | 顶部承载上限 |
|---|---:|---|---:|
| `no_support` | 0.10 | 否 | 0 kg |
| `low` | 0.25 | 是 | 9 kg |
| `ordinary` | 0.45 | 是 | 27 kg |
| `reinforced` | 0.20 | 是 | 54 kg |

异质档位由 `profile_for()` 确定：

```text
u = int(SHA256(canonical_json([version, 20261102, sku_id]))[:8], 16) / 2**32
u < 0.10         → no_support
0.10 ≤ u < 0.35  → low
0.35 ≤ u < 0.80  → ordinary
0.80 ≤ u < 1.00  → reinforced
```

相同版本、种子和SKU得到相同档位；没有逐箱重新抽样。概率不保证在每个小订单里精确兑现。同SKU和同包装档位的属性一致性会被审计。

### 3.3 每个来源生成四个变体

| layer | 具体处理 |
|---|---|
| `source_difficult` | 保留来源快照已有的 `stackable` 和合成承载；这些来源承载本身也不是实测值。 |
| `controlled_base` | 全部指定 `reinforced`，承载54 kg。 |
| `controlled_heterogeneous` | 按上述哈希分档，使用0/9/27/54 kg。 |
| `controlled_capacity_tight` | 沿用同一哈希档位，承载乘0.5，成为0/4.5/13.5/27 kg；`stackable`不变。 |

因此是4来源×4变体＝16任务，箱体出现次数66×4＝264；264不是264个独立来源。两个异质层构成容量单因素配对，来源、尺寸、质量、到货关系保持一致。

### 3.4 写出任务与身份材料

任务含 `task_id`、`source_group_id`、`source_order_key`、`partition`、`container`、`items`、`arrival_order`、缓冲容量和候选上限。当前缓冲容量3，每箱候选上限16、联合上限48；几何姿态为直立0/90度。

固定任务不存摆放位置、支撑关系、当前累计载荷或稳定性答案。任务在运行时才由公共候选、选择、选后监测和物理提交产生轨迹。当前包装任务的 `regions`、`rules` 为空，不引入旧类别相容性或区域语义。

交付包同时写出：

- `tasks/*.json`：16个任务。
- `sku_packaging_map.json`：商品与包装身份对应。
- `split_manifest.json`、`sources/`、`source_manifest.json`：来源隔离和快照。
- `config.snapshot.json`、`configuration_freeze/`：本次消费的冻结规则。
- `audits/`：属性、标定、来源隔离、静态条件等审计。
- `witnesses/status.json`：没有新布局见证，状态保留 UNKNOWN。
- `manifest.json`、源码/物理快照及校验材料：绑定生成结果与代码身份。

静态检查不等于存在可行布局，也不证明在线策略能装完。尺寸/质量可追溯到原始文件，但原始测量准确性尚未独立认证。

## 4. 构建和校验命令的实际约束

以下是当前接口说明，本轮未执行。命令在仓库根目录、已有 Python 依赖环境下运行。

构建器要求：输出位于 `semantic_pallet_planner/outputs/` 内、尚不存在，且被 Git 忽略。普通未放行的新目录满足该条件；已放行的正式历史包不得作为构建目标。

```bash
PYTHONPATH=semantic_pallet_planner/src \
python3 -m semantic_pallet_planner.jev_select build-packaging-dataset \
  --repo . \
  --output semantic_pallet_planner/outputs/LOCAL_PACKAGING_REBUILD_NEW
```

这是重建冻结的四来源包装包，不是任意新来源采样器；它还执行构造物理检查，但不会运行正式订单或模型。若输出目录已存在、未被忽略，或来源/配置身份变化，代码会拒绝。构建完成后的 Git 放行与归档属于后续单独操作，不能通过改旧冻结摘要适配新内容。

既有包静态加载校验接口：

```bash
PYTHONPATH=semantic_pallet_planner/src \
python3 -m semantic_pallet_planner.jev_select validate-packaging-dataset \
  --dataset semantic_pallet_planner/outputs/DATA_JEV_PACKAGING_LOAD_20261102_02
```

现有调用方也可通过 `DatasetOrderAdapter().load(..., spec_config="jev_packaging_load_dataset_v1")` 显式路由。旧协议不应直接接收新任务格式。

## 5. JN4新正式订单的额外门槛

JN4不是直接复用这16个已暴露任务作为独立测试。入口见 `packaging_source_provenance.py` 与 `packaging_evaluation_data.py`：

1. 原始订单及别名、近重复、变体/分叉先组成来源组件。
2. 对组件核验独立可信签发身份、完整历史覆盖、实际使用记录、未知项和证据文件；没有历史命中不等于未见。
3. 只从 VERIFIED_UNSEEN 组件中，按最小原始键的完整箱数分为14—20、21—30、31—40三档，每档2个。
4. 各档按 `digest([20261105, component])` 排序抽取，不按装入量、检索命中或监测成绩筛选。
5. 每来源只生成一个 `controlled_heterogeneous` 任务，保留完整到货序列，复用训练冻结包装标定，保持 UNKNOWN。
6. 加载时重新核验签名、来源/代码/属性身份及来源隔离，再绑定实际任务生成六方法正式计划。

最新来源核验仍为真实合格来源0，三档均不足；[JN4-A缺口验收](../03_阶段产出分析/Jev/Jev_JN4-A真实来源履历核验与冻结缺口验收_20261105.md)明确数据未物化、正式矩阵未冻结、JN4-B不准入。新增语料须另行登记授权，不能通过复制或旋转旧订单制造“新独立来源”。
