# 核心算法开发与验证方案：VLM—几何规划器—动态经验记忆

> 文档版本：V1.0  
> 前置条件：`semantic_pallet_dataset_v1`阶段0验收通过  
> 本阶段定位：使用数据集真值状态和程序化3D可视化，完成几何候选、VLM高层决策与ReMe-style动态经验记忆的完整算法闭环  
> 不纳入本阶段：Gazebo物理、RGB-D感知、MoveIt 2运动规划、Aubo i5执行

## 1. 阶段调整结论

阶段0已经完成“数据、候选、隐藏标注、VLM可见输入、可视化和基础协议”的验收。下一阶段不应立即转向Gazebo，而应先回答论文最核心的两个问题：

1. 在几何规划器提供的安全候选中，VLM能否根据自然语言和3D视觉信息，比纯几何选择更好地满足码垛业务规则？
2. ReMe-style动态程序性记忆能否从过去成功和失败中沉淀可复用经验，并在规则变化时修正过时经验？

因此，本文档将原研究方案中分散的“几何规划—VLM决策—经验记忆”合并为一个完整的阶段1，内部再划分为1A至1E五个里程碑。

```text

```

## 2. 本阶段的边界

### 2.1 本阶段使用什么作为“环境”

本阶段使用一个确定性的真值状态环境，而不是物理仿真：

```text
Scenario JSON
    ↓
读取容器、当前箱体、已放置箱体和自然语言指令
    ↓
EMS-style生成并过滤几何候选
    ↓
选择器返回candidate_id
    ↓
本地协议校验和确定性状态转移
    ↓
更新已码放状态并渲染下一帧3D图像
```

这里的“执行成功”只表示候选通过确定性的边界、碰撞、支撑、重心、可堆叠和承重检查，不代表机械臂已经真实完成抓取与放置。

### 2.2 Gazebo放在哪里

Gazebo明确放到核心算法闭环通过之后，作为最后的机器人验证环节。后续再依次接入：

1. Gazebo真值位姿和尺寸；
2. MoveIt 2可达性、碰撞和路径规划；
3. Aubo i5吸盘抓取与多层放置；
4. Controlled Noise感知误差；
5. RGB-D实际感知闭环。

阶段1内不修改`aubo_ros2_ws`中的现有单层码放区域，也不使用现有固定Z高度逻辑约束算法设计。本阶段只需保证未来输出的候选仍使用统一的`candidate_id + state_hash + request_id`协议，便于后续接入ROS 2。

建议在数据集目录之外新建独立的实验代码目录，例如`semantic_pallet_planner/`。数据集保持只读，实验结果不回写`tasks/`、`candidates/`和`annotations/`。

│   ├── consolidator.py           CREATE/CORROBORATE/REFINE/CORRECT
│   └── verifier.py               回放验证和激活/失效

不强制实际代码必须完全使用这个目录名称，但必须将“数据”、“方法”、“运行日志”和“隐藏评价”分开。

### 4.1 统一选择器接口

所有方法实现相同的最小接口：

```python
class Selector:
    def select(self, request, images=None, memories=None):
        return {
            "request_id": request["request_id"],
            "state_hash": request["state_hash"],
            "candidate_id": "...",
            "confidence": None,
            "reason": "..."
        }
```

选择器不能直接改状态，也不能修改候选坐标。环境只在`resolve_response()`校验通过后提交候选。

### 4.2 一次决策的信息流

```text
数据集真值状态
   → 几何层生成候选
   → 白名单导出器去除隐藏标签
   → 渲染当前码垛区+取料区+候选编号
   → 记忆层检索最多3条active经验
   → VLM选择candidate_id
   → 本地协议校验
   → 提交动作和渲染新状态
   → 动作完成后由隐藏评价器计分
   → 将反馈写入当前方法的独立经验日志
```

## 5. 阶段1A：统一运行器、方法接口与评价器

### 5.1 任务内容

1. 将阶段0中`run_visual_episode.py`的“生成候选—选择—提交—更新”拆分为可复用环境和可插拔选择器。
2. 实现固定Decision Case运行器、完整episode运行器和stream运行器。
3. 建立统一实验配置，保存数据版本、方法、随机种子、候选生成器、模型、prompt、记忆快照和软件环境。
4. 建立统一日志，记录每一步候选数、过滤漏斗、选择、fallback、几何变化、语义得分、延迟、token和记忆事件。
5. 将几何、语义、记忆和API成本指标分开统计，不使用一个总分掩盖问题。

### 5.2 至少实现的基线

| 方法 | 输入 | 选择逻辑 | 用途 |
|---|---|---|---|
| Random-Valid | 合法候选 | 按种子随机 | 最低基线 |
| First/Lowest | 几何特征 | 最低`z_base`、底层优先 | 简单几何基线 |
| Geometry-Greedy | 几何特征 | 当前加权几何分数最高 | 主要确定性基线 |
| Handcrafted-Rule | 结构化真值规则 | 按冻结规则打分 | 显式规则程序上界型基线 |
| Candidate Oracle | 隐藏标注 | 选Oracle最优候选 | 候选集上界，不是可部署方法 |

`Handcrafted-Rule`和`Candidate Oracle`可以读隐藏标注，但必须在方法名和表格中明确标注为上界/评价方法，不能和只看自然语言的VLM当成完全同等的输入方法。

- [ ] 过期`state_hash`、不存在的`candidate_id`、坐标覆盖和响应超时均有测试、日志和确定性fallback。
- [ ] 每步均可由`experiment_id/scenario_id/step/request_id/state_hash`唯一追溯。
- [ ] 至少实现Random-Valid、Geometry-Greedy、Handcrafted-Rule和Candidate Oracle四个选择器。

## 7. 阶段1C：固定候选上的VLM语义决策

### 7.1 为什么先做固定Decision Case

若一开始就让各方法自由运行完整episode，第一步选择不同会导致后续状态全部不同，很难判断差异是否真的来自语义理解。360个固定Decision Case可以保证每个方法面对完全相同的状态、候选和图像，是阶段1中证明VLM语义价值的主实验。

### 7.2 VLM输入模式

| 方法 | 自然语言 | 候选JSON | 3D图像 | 经验 |
|---|---:|---:|---:|---:|
| Geometry-only | 否 | 几何特征 | 否 | 否 |
| VLM-Text | 是 | 是 | 否 | 否 |
| VLM-Visual | 是 | 是 | 是 | 否 |
| VLM+Frozen Retrieval | 是 | 是 | 是 | 固定经验 |
| VLM+Dynamic ReMe | 是 | 是 | 是 | 动态经验 |

VLM一次请求只能包含：

- 当前自然语言指令；
- 容器和当前可见物理状态；
- 当前箱体的尺寸、质量和允许可见的语义属性；
- Top-K合法候选的可见几何特征；
- 当前工作区和候选对比图；
- 当前决策之前已经形成且通过验证的经验。

VLM不能看到`annotations/`、split名称、原始订单标识、Oracle排序、未来箱体和当前时刻之后的反馈。

### 7.3 必须修正C01位置偏差

当前图像与候选列表按几何排序展示，如果永远把几何最优项编为C01，VLM可以通过“总选第一项”取得虚高成绩。因此每个决策点必须：

1. 对候选顺序做确定性随机化；
2. 在当前请求中重新映射`C01...CK`；
3. 图像与JSON使用同一映射；
4. 评价器通过内部映射恢复原`candidate_id`；
5. 保存映射供审计，但不把几何排名放进VLM提示。

### 7.4 VLM响应与失败处理

可执行的最小响应为：

```json
{
  "request_id": "...",
  "state_hash": "...",
  "candidate_id": "C07",
  "confidence": 0.82,
  "applied_rule": "fragile_protect",
  "reason": "该候选不使用易碎箱体作为支撑，且几何代价较小"
}
```

处理顺序固定为：Schema校验→请求标识校验→状态哈希校验→候选存在性校验→本地恢复坐标。最多允许一次格式修复请求；仍失败时退回Geometry-Greedy，且fallback必须计入本方法结果。

### 7.5 评价指标

- 语义规则总得分与各规则分项；
- 相对Geometry-Greedy的配对语义增益；
- 相对Candidate Oracle的regret；
- 在244个非平凡语义Decision Case上的胜/平/负率；
- 最大高度、利用率和几何分数相对Geometry-only的退化；
- 响应Schema通过率、非法ID率、超时率、重试率和fallback率；
- 平均输入/输出token、每步延迟和API成本；
- Test-ID与Language-OOD配对差值。

### 7.6 验收标准

- [ ] Random-Valid、Geometry-only、Handcrafted-Rule、VLM-Text、VLM-Visual和Candidate Oracle在同一批固定Candidate Set上运行。
- [ ] 候选展示顺序已随机化，且选择结果在各显示位置上无明显的“总选C01”偏差。
- [ ] 开发期间只用train/validation调整prompt和重试策略，test划分不参与调参。
- [ ] 所有VLM请求都通过自动数据泄漏扫描，隐藏字段出现数为0。
- [ ] 协议最终合法响应率达到98%以上；任何失败均不会导致非法坐标被执行。
- [ ] 报告所有指标和失败，不丢弃不符合预期的VLM调用。
- [ ] 对VLM-Text与VLM-Visual做配对比较；如果视觉没有改善，如实记录，不将视觉贡献强行设为验收条件。

## 8. 阶段1D：VLM+几何规划器完整episode闭环

### 8.1 任务内容

将阶段1C中通过验收的VLM选择器接入在线episode环境，每一步都根据VLM上一步实际选择后的新状态重新生成候选。不得继续沿用数据集参考轨迹的后续Candidate Set。

```text
step 0：当前状态 → 在线候选 → VLM选择 → 提交
step 1：使用step 0的真实结果 → 重新生成候选 → VLM选择
……
episode结束：统计几何、语义、失败和成本指标
```

固定Decision Case用来做可归因的主比较，完整episode用来评价早期决策对后续布局的累积影响。

### 8.2 验收标准

- [ ] Geometry-Greedy、Handcrafted-Rule、VLM-Text和VLM-Visual至少在validation与Test-ID场景上完成全episode。
- [ ] 每一步都使用当前状态新生成的`state_hash`和Candidate Set，不使用参考轨迹的未来状态。
- [ ] 已提交动作硬约束违规为0；无候选、API失败和fallback都作为正常结果记录。
- [ ] 每个方法的起始Scenario完全一致，但允许因选择不同而出现不同的后续状态。
- [ ] 至少输出3组同一Scenario上Geometry-only与VLM-Visual左右对比动画。
- [ ] 报告固定Decision Case结果和完整episode结果，不把两者混为同一组样本。

## 9. 阶段1E：ReMe-style动态程序性经验记忆

### 9.1 本阶段记忆的正确定位

记忆不是把所有历史prompt重新塞给VLM，也不是记住“SCN_0001选C03”。有效经验应是可迁移的条件化程序知识：

```text
当什么状态特征与规则冲突出现
        → 应优先哪类候选
        → 哪些情况下不应使用这条经验
        → 经验有哪些已验证证据
```

本项目借鉴ReMe的原始日志、文件化记忆、检索以及`CREATE/CORROBORATE/REFINE/CORRECT`生命周期，但需要自己实现码垛领域Schema、反馈评价、回放验证和`policy_scope`。论文中应称为“ReMe-style码垛程序性记忆”或“基于ReMe扩展的领域记忆”。

### 9.2 最小经验卡

```json
{
  "memory_id": "MEM_00017",
  "schema_version": "pallet_memory_v1",
  "status": "candidate",
  "policy_scope": ["heavy_low_v1"],
  "context_signature": {
    "height_regime": "lower_half",
    "attribute_mix": ["heavy", "fragile"],
    "conflict_type": "heavy_vs_fragile_reserve",
    "candidate_pattern": "center_low_available"
  },
  "when_to_use": "底层仍有中心低位候选且当前为重物",
  "procedural_advice": "优先靠中心低放，同时保留连续上表面",
  "when_not_to_use": "候选承重余量不足或当前指令要求品类隔离",
  "evidence": [],
  "verification": {
    "replay_case_ids": [],
    "hard_violation_delta": 0,
    "mean_semantic_gain": null,
    "accepted": false
  },
  "usage": {
    "retrieved": 0,
    "applied": 0,
    "successful": 0,
    "utility_ema": 0.0
  },
  "history": []
}
```

`scenario_id`、`candidate_id`和Oracle得分可以作为`evidence`中的审计指针，但不能进入`context_signature`、`when_to_use`或`procedural_advice`，否则就变成对特定测试样本的记忆。

### 9.3 经验生命周期

1. **获取**：完成动作或episode后，比较VLM选择与Oracle/反例的差异。
2. **抽象**：将具体轨迹压缩为适用条件、程序性建议和禁用条件。
3. **去泄漏审查**：拒绝含有split、未来状态、特定候选ID或测试答案的经验。
4. **候选入库**：新经验先标记为`candidate`，不立即向正式决策注入。
5. **回放验证**：在train/validation中与证据样本分离的决策点上评估经验收益。
6. **激活**：不增加硬违规且达到冻结收益阈值后转为`active`。
7. **检索**：根据当前指令、属性组合、层高区间和候选冲突检索，最多返回3条。
8. **使用评价**：区分“检索到”、“VLM宣称采用”和“采用后产生收益”。
9. **佐证/细化/纠错**：新证据分别触发`CORROBORATE`、`REFINE`或`CORRECT`。
10. **失效**：规则变化或连续负收益时，转为`superseded/deprecated`，保留历史但不再检索。

### 9.4 检索的最小实现

首版只实现BM25或等价的稀疏文本检索，不立即同时加入embedding、向量库和RRF。检索query由以下内容组成：

```text
当前自然语言规则
+ 当前箱体属性摘要
+ 码垛高度区间
+ 候选冲突模式
+ policy_version
```

检索不能使用`scenario_id`、`decision_case_id`、`candidate_id`、split名称、Oracle得分或未来物料。

### 9.5 连续流实验

#### Stationary Stream

规则分布不变，对比随episode增加，记忆是否提高平均语义得分和决策一致性。

#### Policy-Shift Stream

按stream文件冻结的时刻切换规则或优先级，对比：

- 切换后立即性能下降；
- 旧经验的负迁移比率；
- 识别冲突需要的episode数；
- 恢复到预定性能区间的episode数；
- 旧经验被修正或失效所需时间。

### 9.6 记忆消融方法

| 方法 | 检索 | 写入 | 回放验证 | 动态改写 |
|---|---:|---:|---:|---:|
| VLM-NoMemory | 否 | 否 | 否 | 否 |
| Raw-History | 原始历史 | 不形成经验卡 | 否 | 否 |
| Frozen-Retrieval | 是 | 否 | 预先完成 | 否 |
| ReMe-w/o-Verify | 是 | 是 | 否 | 是 |
| ReMe-w/o-Refine | 是 | 是 | 是 | 否 |
| Full-ReMe | 是 | 是 | 是 | 是 |

最简实施顺序为`VLM-NoMemory → Frozen-Retrieval → Full-ReMe → w/o-Verify → w/o-Refine`。`Raw-History`只在API预算允许时增加，避免前期同时维护过多方法。

### 9.7 记忆评价指标

- episode语义得分曲线和AULC；
- 达到固定阈值所需episode数；
- Shift后立即下降量、恢复时间和最终恢复率；
- 检索命中率、经验采用率和采用后平均收益；
- 无关经验率、冲突经验率和负迁移率；
- `CREATE/CORROBORATE/REFINE/CORRECT/DEPRECATE`事件数；
- 新经验验证通过率与被拒绝原因；
- 每条有效经验额外token、延迟和API成本。

### 9.8 验收标准

- [ ] 经验卡通过JSON Schema，具备状态、作用域、适用条件、禁用条件、证据、验证和修改历史。
- [ ] 每个stream从指定的空白或冻结记忆快照开始，不同方法、划分和种子的记忆物理隔离。
- [ ] 每个决策只能读取当前时刻之前的经验和反馈，因果时序测试通过。
- [ ] 测试时Oracle不进入当前决策prompt，仅能在动作提交后用于评价或按试验协议形成延迟反馈。
- [ ] Stationary和Policy-Shift两类stream均能完整运行，并保存每个episode前后的记忆快照。
- [ ] 至少完成VLM-NoMemory、Frozen-Retrieval、Full-ReMe、ReMe-w/o-Verify和ReMe-w/o-Refine五种方法。
- [ ] 能够从日志回放至少一个`CREATE`、一个`REFINE/CORRECT`和一个`DEPRECATE`事件的完整证据链。
- [ ] 记忆的加入与移除不会改变几何候选集，只影响合法候选中的选择。
- [ ] 完整报告AULC、恢复时间、负迁移、经验收益和成本，无论Full-ReMe是否显著优于基线。

## 10. `buffer_size=3`的处理

当前20个`buffer_size=3`场景只有Scenario，没有固定Decision Case和动态选箱候选。这部分不应阻塞`buffer_size=1`主实验。

建议顺序：

1. 先在`buffer_size=1`完成1A—1E的全链路；
2. 再将候选动作扩展为`pick_item_id + pose`；
3. 对缓存中每个物料分别生成并过滤EMS候选；
4. 将物料选择与位置选择绑定在一个不可变候选中；
5. 只做20个配对场景的扩展实验，观察VLM是否能利用语义选择先后顺序。

`buffer_size=3`在阶段1中属于建议完成的扩展项，不属于VLM+ReMe主线的阻塞性前置。

## 11. 数据划分和严格的实验时序

### 11.1 开发与冻结

| 阶段 | 可使用的数据 | 允许做什么 |
|---|---|---|
| 代码开发 | train | 调试接口、prompt、几何权重和记忆流程 |
| 阈值选择 | validation | 选择beam宽度、检索top-k、经验激活阈值和fallback策略 |
| 一次性测试 | Test-ID | 报告主结果，不再调参 |
| 几何泛化 | Geometry-OOD | 评价尺寸/高度分布外 |
| 语义泛化 | Semantic-OOD | 评价未见属性组合 |
| 语言稳健性 | Language-OOD | 与Test-ID做物理等价的配对差值 |
| 经验演化 | Stationary/Shift streams | 严格按时间顺序读取和写入记忆 |

### 11.2 不允许的泄漏

- 用Test-ID选prompt或记忆验证阈值；
- 将Test-ID产生的记忆直接带入Geometry-OOD或Semantic-OOD；
- 将Language-OOD当成全新独立样本扩大样本量；
- 将Oracle解释、结构化真值规则或未来到货信息放进VLM或记忆检索query；
- 对每个方法使用不同Candidate Set，却将差异宣称为VLM或记忆收益；
- 丢弃API失败、fallback、无候选和负迁移样本。

## 14. 阶段1总验收标准

阶段1只有在以下四类条件都满足时才结束。

### 14.1 功能验收

- [ ] 同一运行器可通过配置切换Geometry、VLM和VLM+ReMe选择器。
- [ ] 支持固定Decision Case、完整episode和连续stream三种运行方式。
- [ ] 实现候选顺序随机化、候选ID重映射、响应校验和fallback。
- [ ] 实现经验获取、检索、回放验证、动态改写和失效。
- [ ] 可生成逐步帧、GIF/MP4和方法对比图。

### 14.2 安全与正确性验收

- [ ] 所有实际提交的码放动作经独立验证器检查后硬约束违规数为0。
- [ ] VLM和ReMe不能生成或修改坐标，只能选择当前合法候选ID。
- [ ] 隐藏标注、split、原始来源ID、Oracle和未来状态在当前决策前泄漏数为0。
- [ ] 记忆实验满足时间因果性，每个方法/种子/流都使用隔离快照。
- [ ] 实验可从冻结配置和缓存响应重放，不依赖当前API在线状态。

### 14.3 公平性验收

- [ ] 固定Decision Case上的所有主方法使用相同Candidate Set、相同显示顺序和相同图像。
- [ ] VLM、Frozen Retrieval和Full ReMe使用同一基础模型、prompt模板、视觉输入、token预算和重试策略；唯一主要差异是记忆能力。
- [ ] Language-OOD与Test-ID按`pair_group_id`做配对评价，不当成额外独立样本。
- [ ] API失败、超时、格式错误和fallback全部计入结果。
- [ ] 所有方法报告相同指标、相同场景和相同统计口径。

### 14.4 证据完整性验收

- [ ] 几何对比、VLM Text/Visual消融、记忆消融、ID/OOD与Policy Shift均有可重放结果。
- [ ] 至少对主结果报告均值、中位数、标准差、95%置信区间和配对效应量。
- [ ] VLM/API关键配置至少3个随机种子或重复调用；正式论文关键结论建议5次。
- [ ] 至少有3个成功案例、3个失败/负迁移案例和2个Policy Shift恢复案例的逐步可视化。
- [ ] 至少5个代表场景输出完整3D动画，其中包含至少一个Geometry-OOD、一个Semantic-OOD和一个Policy Shift案例。
- [ ] 生成一份`stage1_acceptance_report.md/json`，列出所有检查、指标、未通过项和已知限制。

### 14.5 如何判断“研究结果”而非“工程通过”

工程验收要求流程正确、公平、可重现，但不应把“VLM必须赢”或“Full-ReMe必须显著提升”写成数据验收条件，否则会引导调参直到得到想要的结论。

阶段1完成后应根据证据做以下判断：

| 结果 | 研究判断 |
|---|---|
| VLM语义得分提高，几何退化可控 | 支持“候选受限VLM语义规划”主张 |
| VLM-Visual优于VLM-Text | 支持视觉信息带来额外贡献 |
| 两者无差异 | 保留VLM候选决策，不强调图像贡献 |
| Full-ReMe提高AULC并缩短Shift恢复 | 支持动态经验演化主张 |
| Frozen与Full-ReMe无差异 | 表明动态改写价值不足，需重新分析记忆任务和更新条件 |
| ReMe持续负迁移 | 报告失败边界，不通过新增规则掩盖 |

## 15. 建议实施顺序与时间

| 里程碑 | 建议周期 | 核心产出 | 退出条件 |
|---|---:|---|---|
| 1A 运行器和基线 | 1—2周 | 统一Selector、日志、指标 | 四个基线和回归测试通过 |
| 1B 几何与动画 | 2—3周 | EMS在线规划、beam、GIF/MP4 | 100个基础场景无程序异常、硬违规0 |
| 1C 固定VLM决策 | 2—3周 | Text/Visual、API缓存、公平对比 | 360个决策点评测链路完整 |

## 16. 阶段1第一个可执行小目标

不要一次就实现全部ReMe和所有基线。第一个开发迭代只做：

1. 新建独立实验目录；
2. 抽取通用Scenario/Decision Case运行器；
3. 实现Geometry-Greedy、Random-Valid和Candidate Oracle三个Selector；
4. 对validation的30个Decision Case运行三个方法；
5. 输出`per_decision.csv + summary.json`；
6. 将`run_visual_episode.py`的选择器改为可配置；
7. 为一个validation场景生成完整GIF/MP4。

这个小目标通过后，再接入第一个VLM API选择器。这样可以确保任何VLM结果都有稳定的传统基线、评价器和回放工具可以对照。

## 17. 与后续Gazebo阶段的交付接口

阶段1向Gazebo阶段只交付以下稳定输入：

```json
{
  "request_id": "episode_001_step_004",
  "state_hash": "...",
  "candidate_id": "...",
  "pick_item_id": "item_007",
  "pose": {
    "x_mm": 0,
    "y_mm": 0,
    "z_base_mm": 230,
    "yaw_deg": 90
  }
}
```

Gazebo/ROS 2适配器后续负责：

- 将mm和容器底面中心坐标转换为m和ROS坐标系；
- 将`z_base_mm`转换为箱体中心高度和机械臂放置位姿；
- 增加MoveIt 2可达性和路径碰撞过滤；
- 执行吸取、搬运、放置和撤离；
- 用Gazebo真值或RGB-D重建新状态。

只要阶段1稳定产出不可变候选动作和可审计选择结果，后续机器人验证就是添加可执行性过滤与状态观测，而不需要重写VLM或ReMe决策逻辑。

## 18. 本阶段最终交付

阶段1最终应形成：

1. 一个可配置的EMS/GOPT-style真值三维码垛实验环境；
2. 一套几何、规则、VLM和Oracle的公平基线；
3. 一个只选择合法候选ID的VLM语义规划器；
4. 一个支持获取、检索、验证、改写和失效的ReMe-style码垛经验层；
5. 固定Decision Case、完整episode、Stationary Stream和Policy-Shift Stream四类实验结果；
6. 一套不依赖Gazebo的3D动画和方法对比演示；
7. 可重现配置、脱敏VLM响应缓存、记忆快照、评价表格和`stage1_acceptance_report`；
8. 向Gazebo/Aubo阶段交付的稳定候选动作接口。

阶段1的中心成果是一条完整、公平、可重现的算法证据链，而不是一段机械臂成功码放的录像。Gazebo、RGB-D、MoveIt 2和Aubo i5将在该证据链稳定后作为最后可执行性验证。
